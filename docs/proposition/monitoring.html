Trois étages, une mesure chacun.Et chaque module à sa place : dans le cœur une fois validé, isolé sinon.

Le monitoring de Sarah Home, de la machine au module : ce que consomment l'équipement, le processus et chaque module (CPU, mémoire, messages MQTT, pire rafale), d'où vient chaque chiffre, ce que la mesure coûte et qui est alerté. Puis la place d'un module : dans le cœur quand il a fait ses preuves, isolé tant qu'il ne les a pas faites, et le passage de l'un à l'autre sans redémarrer le cœur.

Ce que la proposition établitLa machine et le processus se lisent exactement ; le module, selon sa place ; la mémoire du cœur demande une décision.
01 / L'ÉQUIPEMENT

Déjà lu, à compléter

moli-host relève toutes les 15 s. Il manque la pression, les écritures sur la carte, le bridage du Pi, et la santé de Zigbee2MQTT, reçue mais jamais lue.

Proposé
02 / LE PROCESSUS

Exact, sans instrument

/proc donne le temps, la mémoire anonyme, la juste part, le disque. Moli ne lit que VmRSS, qui n'est pas la mesure du budget.

Écart
03 / LE CPU PAR MODULE

Exact dès qu'il a son fil

Le noyau compte chaque fil à la nanoseconde ; tokio 1.54 donne temps occupé et réveils, stables en 64 bits. Avant le fil : TaskMonitor (D8).

Proposé
04 / LA MÉMOIRE PAR MODULE

La seule mesure difficile

Toujours : la mémoire tenue par le kit et la part non expliquée. En option : une étiquette d'un octet. À la demande : isoler pour mesurer.

À trancher
05 / LES MESSAGES

Par module, et la pire rafale

Isolé : le courtier compte sa connexion, ce que rumqttd 0.20 fait sans l'exposer. Dans le cœur : le kit. La rafale de 100 ms compte plus que le débit.

Proposé
06 / LE COÛT

La mesure ne réveille rien

Un relevé par minute, 10 s quand on regarde ; ≈ 342 Kio de courbes ; des agrégats de 15 min en base, 7 jours, jamais archivés.

Calculé
07 / TA RÈGLE

Dans le cœur une fois validé

Relu, vérifié, 7 jours isolé dans son budget : il entre, avec un PIN. Un plantage, une fuite, un budget doublé : il ressort, seul.

Retenu
08 / LA BASCULE

Changer de place à chaud

Le hub retient les ordres ; l'ancienne instance finit et rend 4 Kio ; la nouvelle démarre. Aucun appareil hors ligne, aucun ordre rejoué.

Proposé

Date : 23 octobre 2026. Statut : proposition, aucune modification du code. Base analysée : main au commit a835893, et les sources de rumqttd 0.20.0, tokio 1.54.1 et rustix 1.1.5, lues là où la proposition s'appuie sur elles.

Proposition à part. Elle complète l'analyse V7 (le courtier, § 6 ; l'isolation des modules, § 9.4 ; un fil par pilote, § 20.1), l'étude de haute disponibilité v2 (le pont maison) et la critique des workflows (la zone de travail). Ta seconde idée, redémarrer le moteur sans rien perdre, a son propre document : Redémarrage à chaud.

Ta demande :

  1. Connaître la mémoire utilisée par les équipements, le CPU de l'ensemble, le CPU par module.
  2. La mémoire de chaque module : celui qui gère le pont, les modules API, et les autres.
  3. Le nombre de messages MQTT par module, et le reste : mémoire, CPU…
  4. Hors monitoring : qu'un module tourne dans le cœur quand il a été validé, ou à part ; et qu'on puisse le relancer isolé, ou dans le cœur, comme on le souhaite.

Les questions, reformulées pour être tranchables (« comment pourrait-on… ») :

# Comment pourrait-on… §
1 savoir ce que consomme chaque équipement, chaque processus et chaque module, sans que la mesure coûte plus que ce qu'elle mesure ? 4, 5, 8
2 attribuer à un module la mémoire et le CPU qu'il prend quand il partage le processus du cœur ? 5, 6
3 compter les messages MQTT de chaque module, alors que les modules du cœur partagent un seul lien avec le courtier ? 7
4 voir venir une dérive (une fuite, une boucle, une rafale) avant qu'elle ne touche la maison, sans réveiller personne pour rien ? 3, 10
5 décider où tourne un module, et le faire passer du cœur à l'isolé, ou l'inverse, sans redémarrer le cœur ni perdre un ordre ? 11

Méthode, et techniques employées, nommées au fil du texte :

  • lecture du code : ce que Sarah Home mesure déjà, preuves fichier:ligne (§ 2, annexe B) ;
  • premiers principes : quelles mesures brutes donnent toutes les autres (§ 4) ;
  • remue-méninges inversé : « comment rendre le monitoring nuisible ? » ; chaque réponse, retournée, devient une règle (§ 3) ;
  • questions en étoile : qui mesure, quoi, où, quand, comment, pour qui (§ 4) ;
  • analyse morphologique : les façons de mesurer la mémoire d'un module qui partage le tas du cœur, côte à côte (§ 6) ;
  • analogies : Erlang, dont chaque processus a son tas et se mesure exactement ; Vector, qui étiquette chaque allocation de son composant ; Zigbee2MQTT, qui publie sa propre santé ; Home Assistant, qui n'attribue rien par intégration (§ 6, § 7, annexe A) ;
  • méthode Disney (rêveur, réaliste, critique) sur le passage d'un module du cœur à l'isolé (§ 11.6) ;
  • convergence à critères visibles : exactitude, coût au repos, mémoire, unsafe, effort (§ 12) ;
  • une vérification dans un conteneur : les fichiers /proc et le montage des cgroups, dans un conteneur Docker ordinaire (alpine, noyau 6.8), pour savoir ce qu'on peut lire sans privilège.

Vocabulaire :

  • un équipement est une machine (celle de Sarah Home, la secours, un ordinateur de la maison, le routeur) ou un appareil qui sait dire sa propre charge (Frigate, Zigbee2MQTT) ;
  • un processus est un programme qui tourne avec sa propre mémoire : le cœur (moli-os serve), un module isolé (moli-os module run <id>, V7 § 9.4.2), un voisin (Zigbee2MQTT, moli-archive, Wyoming) ;
  • un module est une brique de Sarah Home qui a son code et sa place dans le contrat MQTT (V7 § 3) : un module api-to-mqtt (une intégration, ce que tu appelles les modules API), le hub, le courtier, le moteur des workflows, le pont maison, le module WebSocket, la base, Sarah ;
  • dans le cœur : le module tourne dans le processus du cœur, sur son fil et son runtime (V7 § 20.1) ; aujourd'hui, sur le runtime partagé ;
  • isolé : le module tourne dans son propre processus et parle au courtier par l'écouteur local (V7 § 9.4.2). À ne pas confondre avec le mode « isolé » d'une machine dans l'étude de haute disponibilité v2 (§ 4), qui désigne une machine coupée de ses pairs ;
  • le pont a deux sens dans les études : le pont maison, qui copie la mémoire vers les secours (HA v2 § 6.4), et les ponts radio (Zigbee2MQTT, demain Matter). Les deux sont mesurés ici ;
  • l'observatoire est le module qui relève les mesures, les range et les sert. Il porte un nom à part pour ne pas le confondre avec le superviseur, qui relance les pilotes (supervisor.rs) ;
  • l'astreinte est la personne qui reçoit les alertes techniques, le propriétaire, et pas la famille (ARCHITECTURE, « l'astreinte lira ce journal ») ;
  • le gardien est le petit processus qui reste quand le cœur redémarre : il lance les modules isolés et garde ce qui doit survivre. Il est décrit dans le document Redémarrage à chaud.

1. Le verdict en bref

  • Trois étages, une source de vérité chacun. L'équipement se lit dans /proc et /sys, ce que fait déjà moli-host toutes les 15 s. Le processus se lit dans /proc/<pid>, exactement, sans une ligne de code dans le programme mesuré. Le module se lit selon sa place : isolé, c'est son processus ; dans le cœur, c'est son fil, ses compteurs et, pour la mémoire seulement, une estimation ou une étiquette.
  • Le CPU par module est exact dès qu'un module a son fil. C'est la couche 1 de la V7 (un fil et un runtime par pilote, § 20.1). Le noyau compte alors le temps de chaque fil, en nanosecondes (/proc/self/task/<tid>/schedstat), et tokio 1.54 donne, sans option instable sur une machine 64 bits, le temps occupé et le nombre de réveils de chaque runtime. Tant que tous les pilotes partagent le runtime, comme aujourd'hui, TaskMonitor (décision D8, jamais faite) donne une approximation.
  • La mémoire par module est la seule mesure difficile. Un tas partagé ne sait pas à qui appartient un octet, et un octet alloué par un module est souvent libéré par un autre fil : le courtier garde les messages dans ses segments. Je propose quatre niveaux :
    • toujours, la mémoire de ce que le kit tient pour le module : files, voies, caches ;
    • toujours, la part que ces comptes n'expliquent pas, entre ce total et la mémoire anonyme du cœur ;
    • en option de construction, une étiquette d'un octet par allocation, comme Vector, à mesurer sur le Pi ;
    • la vérité de terrain, à la demande : relancer le module isolé et lire sa mémoire exacte.
  • Les messages MQTT par module, sans rien ajouter au chemin des messages.
    • Isolé : le courtier compte sur sa connexion. rumqttd 0.20 tient déjà un compteur d'entrée par connexion, mais ne l'expose pas, et sa table par sujet fuit. Notre version le corrige.
    • Dans le cœur : le kit compte, par une addition atomique par message.
    • Zigbee2MQTT publie déjà ses propres comptes sur bridge/health, que moli-z2m reçoit sans le lire.
    • Montrer la pire rafale, pas seulement le débit : la V7 a montré que c'est elle qui fait décrocher (§ 17.1.2).
  • La mesure ne réveille rien et n'écrit presque rien.
    • Un relevé par minute ; toutes les 10 s seulement quand quelqu'un regarde la page Système.
    • Les modules ne sont jamais réveillés : on les lit de l'extérieur.
    • En mémoire, ≈ 342 Kio de courbes pour 40 modules, 24 h au pas de 5 min.
    • Sur la carte : des agrégats de 15 min dans la famille diagnostic de l'historique, 7 jours, jamais archivés.
  • Où tourne un module : dans le cœur une fois validé, isolé sinon. C'est ta règle. Elle tient sur les critères de la V7 (§ 9.4.2), avec des preuves pour « validé » : relu, vérifié par le catalogue, 7 jours isolé sans incident et dans son budget.
    • Isolé : un module nouveau, écrit par un agent, en code tiers ou en FFI, déjà planté, ou au-dessus de son budget.
    • Dans le cœur, toujours : le hub, le courtier, le moteur, l'API, et les modules qui partagent la passerelle HTTP de l'API.
    • Rentrer dans le cœur demande un humain. Retourner à l'isolé peut être automatique : c'est le sens sûr.
  • Passer d'une place à l'autre se fait à chaud, sans redémarrer le cœur, parce que le même code est dans le binaire (V7 § 9.4.2).
    • Le hub retient les ordres dans leurs voies.
    • L'ancienne instance finit et rend un petit état (≤ 4 Kio), puis la nouvelle démarre dans l'autre mode.
    • Les appareils restent « en bascule », jamais « hors ligne », et aucun ordre n'est rejoué après son échéance.
  • Un module isolé est lancé par le gardien, pas par le cœur : il survit ainsi au redémarrage du cœur. C'est le lien avec ta seconde idée, et le sujet du document Redémarrage à chaud.

3. Remue-méninges inversé : comment rendre le monitoring nuisible ?

La question à l'envers fait sortir les règles plus vite que la question à l'endroit. Chaque idée pour nuire devient une règle, en la retournant :

# Pour nuire, on pourrait… La règle qui en sort
N1 relever tout chaque seconde, et réveiller chaque module pour qu'il se mesure un relevé par minute ; 10 s seulement quand la page Système est ouverte ; les modules se lisent de l'extérieur, jamais réveillés
N2 écrire chaque relevé sur la carte SD le fin en mémoire, 24 h ; en base, seulement des agrégats de 15 min, 7 jours, famille diagnostic, jamais archivés
N3 prendre plus de mémoire que les modules mesurés un budget fixe : ≈ 342 Kio pour 40 modules ; des entiers de 16 bits, pas des flottants de 64
N4 afficher VmRSS et l'appeler « mémoire » la mémoire anonyme, comme le budget ; Pss quand des processus partagent le binaire
N5 attribuer à un module ce qu'un autre a libéré, et voir une fuite qui n'existe pas une mémoire par module est mesurée, étiquetée ou estimée, et l'écran dit laquelle
N6 montrer un module « à 0 % » parce qu'il est mort un module mort est mort, pas sobre : statut d'abord, mesures ensuite
N7 moyenner sur 5 min et rater la rafale de 5 000 messages qui fait décrocher le moteur la pire rafale sur 100 ms est une mesure à part entière (V7 § 17.1.2)
N8 alerter la famille à 3 h du matin parce qu'un nuage a répondu lentement les alertes vont à l'astreinte, groupées par incident ; rien aux heures calmes, sauf si l'alarme, une serrure ou un détecteur est touché
N9 laisser un compteur déborder et repartir de zéro, pour faire croire à une chute des compteurs de 64 bits qui ne font que monter ; les débits se calculent par différence
N10 perdre toutes les courbes à chaque redémarrage elles passent au cœur suivant par le relais du gardien (document Redémarrage à chaud)
N11 laisser un agent changer la place d'un module lire : oui ; changer : une demande, qu'un humain valide (la garde, 202)
N12 mesurer avec une sonde qui exige root ou le socket Docker uniquement ce qu'un processus non privilégié lit : /proc, /sys, son propre cgroup
N13 montrer cent courbes, et aucune réponse à « est-ce que la maison tient ? » une ligne en tête : la maison tient, ou non, et pourquoi ; le détail ensuite
N14 taire une perte de messages, comme rumqttd 0.20 au-delà de ~1 400 messages de retard (V7 § 6.1) toute perte signalée par le courtier déclenche une alerte, dès la première

4. Trois étages, et ce qu'on mesure à chacun

Premiers principes. Toutes les mesures se déduisent de cinq grandeurs brutes, que le noyau ou nos propres compteurs donnent sans calcul :

  1. un temps passé sur le processeur, en nanosecondes, par fil ou par processus ;
  2. une mémoire résidente, en octets, par processus, anonyme d'un côté, fichier de l'autre ;
  3. des octets alloués, par module, quand le module partage le tas du cœur ;
  4. des compteurs qui ne font que monter : messages, octets, appels, erreurs, relances ;
  5. l'heure du relevé.

Les pourcentages, les débits, les tendances et les alertes se calculent ensuite, par différence entre deux relevés. Questions en étoile sur chaque mesure : qui la produit, qui la lit, où elle vit, combien de temps, à quel rythme, pour qui. Les tableaux qui suivent y répondent.

Ce que j'ai vérifié dans un conteneur Docker ordinaire (alpine 3.20, noyau 6.8, sans privilège) : smaps_rollup, le schedstat d'un fil, io et /proc/pressure répondent. Le système de fichiers des cgroups est monté en lecture seule : mkdir /sys/fs/cgroup/essai répond Read-only file system. Dans Docker, on ne peut donc pas créer un cgroup par module isolé. On mesure son processus par /proc, et sa limite de mémoire passe par setrlimit (V7 § 9.4.2 prévoyait « cgroup ou RLIMIT_AS »). Sous systemd, le gardien peut recevoir un sous-arbre de cgroups (Delegate=yes) et donner à chaque module isolé le sien, avec sa propre limite.

5. Le CPU d'un module dans le cœur

Aujourd'hui, une approximation. Tous les pilotes partagent le runtime (supervisor.rs:31). Le noyau ne voit que les fils de tokio, pas les pilotes. TaskMonitor de tokio-metrics (0.5.2), décidé par D8, instrumente une tâche et donne, entre autres, la durée moyenne d'un poll, la part des poll lents, la durée moyenne d'attente et d'inactivité. La somme des durées de poll d'un pilote est une bonne approximation de son CPU, avec deux défauts :

  • un appel bloquant fait dans un poll compte comme du calcul ;
  • un fil que le système suspend au milieu d'un poll compte aussi.

Avec un fil par module (V7 § 20.1), une mesure exacte. Chaque module a son fil, nommé pilote-<instance>, et son runtime current_thread. Deux mesures en sortent :

  • le noyau compte le temps de ce fil sur le processeur, en nanosecondes ; l'observatoire le lit de l'extérieur, sans réveiller le module ;
  • tokio 1.54 donne pour ce runtime le temps occupé (worker_total_busy_duration) et le nombre de fois où il s'est endormi puis réveillé (worker_park_unpark_count). Dans les sources de tokio 1.54.1, ces deux mesures sont sous cfg_64bit_metrics! : stables, sans tokio_unstable, sur une machine 64 bits comme le Pi Zero 2 W sous un système 64 bits. Le reste des métriques par worker demande tokio_unstable (runtime/metrics/runtime.rs:104-249).

Les réveils sont la mesure qui prouve la règle « une brique inactive ne coûte rien » (PERFORMANCE.md) : un module au repos ne se réveille pas. D8 le visait avec « 0 poll » ; le fil par module le donne directement.

Le CPU qu'un module fait dépenser aux autres. Un module qui publie beaucoup fait travailler le courtier (3,3 µs de CPU du routeur par message, V7 § 11.4.5) et le hub. Ce coût n'est pas sur son fil. L'écran le montre à part, comme coût induit : messages × coût unitaire mesuré. Il n'est jamais ajouté à son CPU propre.

6. La mémoire d'un module dans le cœur : la seule mesure difficile

Pourquoi c'est difficile. Dans le cœur, tous les modules partagent un tas et un allocateur : celui de musl, que la V7 garde (§ 11.4.6). Un octet ne sait pas qui l'a demandé. Pire, il change souvent de main : un module construit un message, et c'est le fil du courtier qui le libère, quand le segment qui le garde tourne. Un compteur par fil se trompe donc dans les deux sens : le module semble fuir, le courtier semble rendre de la mémoire qu'il n'a jamais prise.

Analogie : Erlang. Chaque processus Erlang a son propre tas. process_info(Pid, memory) donne « la taille en octets du processus », pile, tas et structures internes comprises, et reductions le travail qu'il a fait. La mesure est simple parce que les tas sont séparés, pas parce que l'instrument est plus fin. La leçon vaut ici : la mémoire d'un module n'est exacte que s'il a sa propre mémoire, c'est-à-dire s'il est isolé.

Analyse morphologique : les façons de mesurer, côte à côte.

  2. Toujours, la part non expliquée. C'est la mémoire anonyme du cœur, lue dans le cgroup comme le budget, moins ce que les comptes expliquent : les modules (A) et les structures du hub, dont la V7 donne la taille (§ 11.4). Tant qu'elle reste plate, rien à dire. Si elle monte, un module fuit hors de ce que le kit voit, et l'observatoire propose l'étape 4.
  3. En option de construction, l'étiquette (C), telle que Vector l'a faite (v0.27.0, décembre 2022, --allocation-tracing) : un octet de numéro de module après chaque allocation.

    • Passer au binaire de mesure coûte un redémarrage, qui ne perd rien avec le document Redémarrage à chaud.
    • L'écran affiche alors « étiquetée ».
    • Une limite, comme chez Vector : la mémoire est comptée à qui l'a allouée, même si un autre la garde. Un message construit par un module et gardé par le courtier reste compté au module. C'est la bonne réponse à « qu'est-ce que ce module fait garder ? ».
  4. À la demande, isoler pour mesurer (E). « Mesurer exactement pendant 24 h » relance le module isolé, lit sa mémoire exacte, puis le remet à sa place. L'écran affiche « mesurée ».

Une exception à une règle du dépôt. Un allocateur global s'écrit avec unsafe (unsafe impl GlobalAlloc), et l'espace de travail l'interdit (unsafe_code = "forbid", Cargo.toml:110). Deux voies :

  • une crate à nous d'une soixantaine de lignes, seule exception nommée, relue et passée sous Miri ;
  • la crate tracking-allocator (0.4.0), qui porte l'unsafe à notre place.

Comme l'option ne vit que dans le binaire de mesure, le binaire de production reste sans unsafe.

7. Les messages MQTT, module par module

Les modules isolés : le courtier compte, sur leur connexion. Chacun a sa connexion à l'écouteur local (V7 § 9.4.2). Ce que rumqttd 0.20.0 fait, lu dans ses sources :

  • un compteur d'entrée par connexion existe : chaque publication reçue passe par IncomingMeter::register_publish (router/routing.rs:641-642), qui tient un total en nombre et en octets, et une table par sujet, la fuite relevée par la V7 (« chaque connexion garde un compteur par sujet publié, 73 o », § 6.1) ;
  • la sortie n'est pas comptée : la ligne qui ajouterait la taille est commentée (routing.rs:702-703) ;
  • rien de cela n'est exposé : send_meters ne publie que le compteur du routeur (connexions, abonnements, publications et échecs, ces deux derniers remis à zéro à chaque lecture) et un compteur par filtre d'abonnement (routing.rs:1152-1160, router/mod.rs:272-279, :307-312) ;
  • l'alerte de perte CursorJump { filter, lost } existe (router/alertlog.rs:8-10), mais la V7 a mesuré que son lost reste à 0.

Dans moli-courtier, notre version : garder les totaux par connexion, dans les deux sens, en nombre et en octets ; supprimer la table par sujet ; exposer ces compteurs au hub ; corriger lost. Ce sont des endroits que la V7 touche déjà pour les ACL et le signal de perte (§ 6.1).

Les modules du cœur : le kit compte. Ils partagent un seul lien avec le courtier (« les modules du binaire partagent un seul lien abonné à cmd/# ; le kit répartit par module », V7 § 6.4). Le courtier ne peut donc pas les distinguer. Le kit le peut : chaque publication et chaque ordre réparti passent par lui. Coût : une addition atomique Relaxed par message, de l'ordre de la nanoseconde, à 239 messages par seconde à la pointe des deux maisons (V7).

Les clients extérieurs (Zigbee2MQTT, appareils MQTT) : leur connexion, comme un module isolé, et ce qu'ils disent d'eux-mêmes (bridge/health pour Zigbee2MQTT, § 4.1).

Par famille de sujets. in/, val/, cmd/, req/, res/, evt/, wf/, sys/, repl/ : rumqttd tient déjà un compteur par filtre d'abonnement (SubscriptionMeter, nombre et taille). Notre version l'expose tel quel.

La rafale, plus que le débit. La V7 l'a mesuré : « ce n'est pas le débit qui fait décrocher le moteur actuel, c'est la profondeur d'une rafale instantanée » (§ 17.1.2). Le kit garde donc, pour chaque module, le plus grand nombre de messages publiés en 100 ms depuis le dernier relevé. Un pont qui republie tout à sa reconnexion se voit tout de suite.

  • il a été relancé 3 fois en 10 min.

11.3 Ce que « validé » veut dire

Une liste de preuves, gardées avec la version exacte du module (l'empreinte du binaire) :

  1. relu : un humain l'a validé, avec son PIN (règle 9) ;
  2. vérifié : moli-os catalogue check passe, fixtures rejouées ;
  3. observé : 7 jours isolé, sans panique ni relance anormale ;
  4. dans son budget : mémoire, CPU, messages, rafale ;
  5. stable : aucune mémoire qui monte sans redescendre sur la période ;
  6. sans unsafe ni FFI, ou alors il reste isolé quoi qu'il arrive.

Une nouvelle version repart de l'étape 3 : elle tourne isolée pendant que l'ancienne a cédé sa place. Le document Redémarrage à chaud montre qu'une version neuve d'un module peut même tourner isolée à côté d'un cœur resté à l'ancienne version, tant que le contrat moli/v1/ ne change pas.

11.4 Passer de l'un à l'autre, à chaud

Pas besoin de redémarrer le cœur. Le même module est compilé dans le binaire et tourne aussi dans un petit exécutable (V7 § 9.4.2). Changer de place, c'est arrêter une instance et démarrer l'autre :

  1. Retenir. Le hub marque le module « en bascule ».
    • Ses ordres attendent dans leurs voies, avec leur échéance inchangée.
    • Ses appareils gardent leur valeur et leur qualité.
    • La santé suspend leur échéance « muet » le temps de la bascule, 10 s au plus. Aucun automatisme ne voit un appareil « hors ligne ».
  2. Finir. L'ancienne instance cesse de prendre des ordres.
    • Elle finit l'ordre en vol en 1 s au plus ; au-delà, son issue est « incertaine » (V7 § 20.7).
    • Elle vide son tampon de sortie : valeurs, occurrences, issues.
  3. Passer. Elle rend son état de module, 4 Kio au plus (des curseurs, des abonnements, ce qu'elle veut retrouver), et s'arrête : son fil est rejoint, ou son processus sort. Jamais un secret : les secrets restent au coffre, et chaque instance les relit.
  4. Lancer. La nouvelle instance démarre dans l'autre mode, avec cet état.
  5. Reprendre. Elle se reconnecte à ses appareils, republie sa disponibilité et ses valeurs ($vu). Le hub libère les ordres en attente dont l'échéance court encore. Ceux qui sont échus sont refusés, jamais rejoués : c'est la règle de toujours.

Jamais deux instances à la fois. Deux instances seraient deux écrivains pour les mêmes appareils, et certains modules prennent un identifiant MQTT fixe : deux instances « se chassent du courtier » (HA v2 § 2.4, pour Bambu, Frigate et Zigbee2MQTT).

La durée est celle de la reconnexion du module à ses appareils : d'une fraction de seconde pour un appareil local à quelques secondes pour un cloud. L'écran l'annonce avant le geste : « environ 2 s sans ordre pour 4 appareils ».

11.5 Qui lance un module isolé

Le gardien, pas le cœur. Si le cœur lançait ses modules isolés, ils seraient ses enfants. Dans un conteneur, la mort du processus principal arrête tous les autres, et ils mourraient avec lui. Lancés par le gardien, ils survivent au redémarrage du cœur. Ils gardent leurs connexions aux appareils et leurs tampons, et se reconnectent au courtier dès qu'il revient. C'est ce qui rend possible ta seconde idée, décrite dans Redémarrage à chaud.

Le gardien lance un module avec son compte auprès du courtier. Il lui passe un jeton par lancement, par un tube hérité, jamais dans l'environnement ni sur la ligne de commande : les deux se lisent dans /proc. C'est la règle des secrets du dépôt (« par un tube, jamais au clavier ni affiché »). Le gardien le relance s'il meurt, avec la même attente croissante que le superviseur, de 1 s à 60 s.

11.6 La bascule, vue par le rêveur, le réaliste et le critique

Méthode Disney.

  • Le rêveur : chaque module change de place d'un geste, à tout moment, sans que personne ne le remarque. On essaie la version neuve d'un module isolée, à côté de l'ancienne, et l'on bascule quand elle a fait ses preuves.
  • Le réaliste :
    • les modules qui partagent la passerelle HTTP de l'API ne sortent pas du cœur ;
    • un processus coûte 577 Kio ;
    • une reconnexion au cloud prend quelques secondes et compte dans les limites du fabricant ;
    • deux instances du même module ne doivent jamais tourner ensemble, donc « à côté » veut dire « l'une après l'autre ».
  • Le critique :
    • une bascule qui échoue au milieu laisse un module nulle part. Il faut donc un retour automatique à l'ancienne place si la nouvelle instance n'est pas prête en 30 s ;
    • une bascule pendant une rafale prolonge la rafale. Elle attend donc que le tampon d'entrée soit vide ;
    • une bascule aux heures calmes réveille des appareils. Le geste les signale et propose d'attendre.

Ce qui en reste, dans le § 11.4 : arrêt puis départ, jamais en parallèle ; retour à l'ancienne place après 30 s sans nouvelle instance prête ; pas de bascule pendant une rafale.

12. Les choix, à critères visibles

La mémoire d'un module du cœur (✓ bon, ~ moyen, ✗ mauvais) :

Option Exacte Coût au repos Mémoire en plus Sans unsafe en production Effort Retenue
A. Tenue par le kit ~ ✓ ✓ ✓ ✓ toujours
B. Compteur par fil ✗ (débit : ✓) ✓ ✓ ✗ ~ comme débit, dans le binaire de mesure
C. Étiquette d'un octet ✓ ~ ~ à mesurer ✓ (option de construction) ~ option de construction
D. Une arène par module ✓ ~ ✗ ✓ ✗ non
E. Isoler pour mesurer ✓ ✓ ~ (577 Kio, le temps de la mesure) ✓ ✓ (avec la bascule) à la demande

Où ranger les courbes :

Option Écritures Survit à un redémarrage Mémoire Retenue
En mémoire seulement 0 non ✓ —
En base, chaque relevé ✗ (40 × 6 par minute) oui ✓ non
Dans l'instantané horaire (HA v2) ~ (il quintuplerait : de 233 Kio à plus d'1 Mio) oui ✓ non
24 h en mémoire, passées par le relais ; agrégats de 15 min en base ✓ (23 040 lignes par jour, en lots) oui (à chaud : tout ; à froid : les agrégats) ✓ (≈ 342 Kio) oui

Le rythme : fixe à 10 s (✗ au repos), fixe à 60 s (✓ au repos, ~ pour diagnostiquer en direct), adaptatif : 60 s, 10 s quand on regarde (✓ et ✓). Retenu : adaptatif.

Changer de place : redémarrer le cœur (✗ : tout s'arrête), arrêt puis départ, à chaud (✓), deux instances en parallèle (✗ : deux écrivains). Retenu : arrêt puis départ.

Qui lance un module isolé : le cœur (✗ : il meurt avec lui), le gardien (✓ : un seul mécanisme, sous Docker et sous systemd), une unité systemd par module (~ : parfait sur le Pi, impossible sous Docker, et il faudrait piloter systemd depuis le cœur). Retenu : le gardien ; sous systemd, il reçoit un sous-arbre de cgroups pour donner à chaque module isolé sa limite et ses comptes.

13. Le plan

Chaque marche est utile seule, dans l'ordre :

  1. Lire ce que le noyau donne déjà (aucun changement d'architecture) :
    • RssAnon et VmHWM à la place de VmRSS ;
    • la mémoire anonyme du cgroup, pour suivre le budget en continu ;
    • /proc/self/io ;
    • la pression, les écritures sur la carte, le bridage du Pi ;
    • bridge/health de Zigbee2MQTT.
  2. Un fil par module (V7 § 20.1). Le CPU par module devient exact : le temps noyau de chaque fil, le temps occupé et les réveils de son runtime. Avant cela, TaskMonitor (D8) donne une approximation.
  3. Les compteurs du kit et de moli-net : messages, octets, pire rafale, appels, erreurs, issues.
  4. L'observatoire :
    • ses courbes en mémoire ;
    • ses agrégats dans la famille diagnostic ;
    • /api/system/modules ;
    • la page Système, et l'outil MCP.
  5. Les compteurs par connexion dans moli-courtier, avec la V7 (§ 6.1).
  6. Le gardien, et la place d'un module : moli-os module run, la bascule à chaud, l'état de module, la rétrogradation automatique (document Redémarrage à chaud, pour le gardien).
  7. Les alertes à l'astreinte, et les budgets dans les paquets.
  8. L'étiquette mémoire, en option de construction, après la mesure M3 sur le Pi.
