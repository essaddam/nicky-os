01 · Le master démarre en premier

Prototype vérifié

Son port HTTP loopback est ouvert avant la planification et les enfants. Le master appelle un exécutable adjacent connu pour obtenir les IDs des groupes, puis lance le broker et les hôtes. Il surveille disponibilité de processus, heartbeat, RSS et CPU. Il reste séparé même lorsque tous les modules sont fusionnés.

1 · Master minimal · processus séparé

HTTP GET /health et /status → plan → lancement → surveillance → arrêt des enfants.

2 · Groupe confort

TaHoma + Ariston + météo/soleil. Tas et connexion MQTT du processus partagés.

3 · Groupe médias

Apple TV + moteur musical local. Peut être séparé davantage au démarrage.

Transport MQTT entre groupes

Broker dans un autre enfant ; en mode fusionné, broker et modules partagent le même enfant. Le master ne traite pas leurs états.

Surface bornée : trois routes GET, aucun corps de requête, 16 connexions, en-têtes de 8 Kio et délai de 2 s. Ni API d’écriture, ni téléchargement de plugins, ni interface de commande. La configuration et le binaire adjacent restent des fichiers locaux de confiance.

Binaire master sur disque

1,10 Mio

Taille du fichier release ; ce n’est pas sa RAM.

RSS master observée

2,48–2,72 Mio

Échantillons du master seul pendant les essais ; aucune borne OS imposée.

Code métier dans le master

Absent

Code séparé et recherche de symboles : Ariston, Overkiz, MQTT et codecs audio absents de cet exécutable.

Une configuration incorrecte ou un enfant mort laisse le HTTP du master disponible. SIGINT/SIGTERM annulent le démarrage, arrêtent et récoltent ses enfants. Ce lot ne remplace pas encore le démarrage de production de Moli ; un superviseur système doit aussi couvrir le master lui-même.

02 · Les modules sont sélectionnés au démarrage

Un même module conserve ses identifiants d’appareils, points et topics lorsqu’il change de groupe. Le plan refuse les doubles propriétaires d’une même source, les affectations ambiguës et les modules actifs sans groupe. Un module désactivé ne construit pas son adaptateur.

Un groupe est ici un processus, avec son tas et son allocateur. Ce POC ne crée pas de conteneur OCI, de sandbox ou de mémoire partagée entre processus. La mémoire commune dans un groupe est un tas ordinaire ; un IPC ou mmap pourra être ajouté après mesure du besoin.

Le banc de topologie comprend un parent broker/observateur, pas le master. Les nombres de processus diffèrent donc du tableau de démarrage. Les pics ne sont pas nécessairement simultanés ; leur somme n’est ni une mesure de pages physiques uniques ni une limite mémoire. Les mesures CPU reposent sur des compteurs ps par centième de seconde et une fenêtre de quelques secondes : 0,00 % peut signifier une activité sous leur résolution. Le coût des processus ps utilisés pour mesurer n’est pas compris ; il faudra mesurer la supervision elle-même sur la cible de déploiement.

Les temps moyens incluent observation, validation, comparaison et sérialisation des deltas du module. Ils excluent le transport et ne sont pas des délais de réponse d’un appareil. Les conteneurs Value excluent les clés, index, métadonnées et annexes de texte. Les capacités de tables excluent les en-têtes d’allocateur et Arc. Aucune RSS par module n’est inventée dans un tas partagé.

Optimisations présentes et limites

Les tables enum sont compactes à la frontière ; l’état conserve un code numérique. Les descriptions sont transférées depuis l’adaptateur une fois. Les états sont comparés et publiés seulement lorsqu’ils changent, avec une sérialisation qui emprunte leur contenu. Un groupe partage sa connexion MQTT et son runtime ; les séparer augmente les ressources répétées, mais réduit le périmètre d’une panne.

Les textes courants, les dernières valeurs et les schémas de cet outil sont encore en mémoire. Il ne démontre pas encore la politique disque du serveur 1414, un layout inline de production, ni l’élimination des allocations JSON de l’ancien pont HA. Les 114 Mio et les buffers de l’analyse précédente restent attachés à leur campagne : aucun gain de ces nouvelles petites fixtures ne leur est soustrait.

04 · Description retained, états différentiels et générations

moli-probe/module/<id>/config
moli-probe/module/<id>/state/<PointId>
moli-probe/module/<id>/availability
moli-probe/module/<id>/simulate
moli-probe/module/<id>/command-result

Le catalogue indique code, valeur native, libellé et version. L’état transporte valeur, qualité, séquence, génération d’instance et révision de description. Un client attend la bonne description avant d’interpréter un code. Une nouvelle génération invalide les valeurs et la disponibilité de l’ancienne ; les observations arrivées avant la description attendent dans un tampon borné.

Les commandes d’essai sont non retained, à génération exacte, identité bornée, expiration maximale de cinq secondes et déduplication bornée. L’enveloppe est limitée à 1 024 octets, le corps natif à 256. Une surcharge avant admission est comptée et ne bloque pas la boucle réseau. Cela ne constitue pas encore le raccord à la garde du moteur de production.

Les textes libres sont acceptés jusqu’à 4 096 octets UTF-8 ; un dépassement est refusé, sans troncature. Cette borne est un contrat d’essai, pas la décision finale entre texte inline et annexe. Les grands catalogues musicaux devront être paginés et rester hors des états retained courants.

Le master publie ici ses mesures par HTTP. Sa télémétrie complète n’est pas encore republiée sur MQTT. Une mort brutale est visible dans le master, mais les appareils nécessitent encore un bail de fraîcheur MQTT ; un heartbeat de processus ne prouve pas la fraîcheur de leurs données.

05 · Le premier chemin audio natif fonctionne

Le moteur local fourni par l’agent Music est une bibliothèque Rust autonome. Son chemin vérifié est : catalogue de deux pistes synthétiques → file révisionnée → décodeur Rust → sortie Null ou WAV. Il se construit et se restaure à l’arrêt. Play/pause/resume/seek/stop et la fin de fichier sont testés.

Essai autonome Null / WAV

9600 frames

48 kHz, stéréo ; contenu PCM et empreinte identiques entre les sorties ; WAV de 38 444 octets.

Essai par MQTT

5824 frames

11648 échantillons effectivement décodés vers NullSink après play ; aucune sortie physique.

File PCM bornée du moteur

16 Kio

4 slots au maximum ; consommateur lent sans avancement de lecture ni croissance sans borne.

Le PCM circule par blocs, jamais en JSON ni en MQTT. Le banc modulaire rend un bloc par tick d’essai ; il vérifie le raccord de contrôle et le décodage, pas la cadence audio temps réel. Le fichier WAV canonique PCM16 stéréo 48 kHz est le seul format qualifié dans ce T0 ; le FLAC reste refusé.

La cible reste un moteur complet comparable fonctionnellement à Music Assistant. Bibliothèque durable, fournisseurs, flux autorisés, DSP, gapless, vrais Cast/AirPlay/Alexa et horloges multiroom restent à développer et à qualifier séparément. Le travail fournisseur/lecteurs de l’agent Music dans tools/music-poc est distinct ; il n’est pas présenté ici comme une sortie matérielle validée. API et bornes du moteur.

Les cinq scénarios de topologie réussissent. Les trois modes actifs de base ont une empreinte sémantique initiale identique. L’essai isolé arrête uniquement son enfant Apple TV et conserve les autres groupes ainsi que la santé du master.

Deux régressions reproduites puis corrigées

  • Un groupe de 32 modules météo bloquait l’initialisation MQTT : le test expirait après six secondes. Les notifications inutiles sont filtrées et la file d’admission ne bloque plus la boucle réseau ; le même test passe avec 1 216 valeurs.
  • Le changement de génération conservait des valeurs et une disponibilité de l’ancienne instance. Le test échouait sur la présence d’une ancienne valeur ; ces observations sont maintenant purgées avant le rejeu correspondant à la nouvelle description.
