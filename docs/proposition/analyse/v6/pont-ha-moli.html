Corrections éprouvées pendant ce lot

  • Overkiz perdait le permis vivant après la séparation de la tâche d’envoi ; il l’emporte maintenant jusqu’à la frontière HTTP.
  • Les commandes admises dans une ancienne génération ne peuvent pas être réactivées après un aller-retour de propriétaire.
  • Les imports Python absolus et l’abonnement de commande inversé étaient masqués par les seuls tests purs ; le chargement avec le vrai framework les a révélés.
  • L’accès au registre d’appareils HA utilise maintenant la résolution par identifiant, et les preuves de migration reprennent le nonce du consommateur Moli.
  • Un état retained explicitement indisponible ne rend plus le proxy disponible. Position et fermeture restent inconnues sans feedback observé.
  • Les battements live5s expirent après15s ; un ancien birth retained ne renouvelle pas la disponibilité.

Bascule et autorité

Le registre est préparé avant tous les pilotes natifs. Une instance déclarée sous migration démarre fermée, même pour un appareil encore inconnu. Pour passer vers Moli : préparer → observer l’ancien écrivain arrêté et quiescent → accorder le nouveau propriétaire après décision durable. Le retour vers HA suit les phases inverses. Une erreur de transport ne change jamais le propriétaire.

Une erreur de stockage après renommage produit un état incertain : fermeture, rechargement et défi neuf, sans rollback aveugle ni répétition. Une fermeture d’urgence ne réouvre jamais la même génération. Les identités, versions et empreintes empêchent une ancienne preuve de valider un autre plan.

L’API expose lecture, prepare, advance, reconcile et reload. Les mutations exigent une session humaine avec PIN, refusent invités et mode démo, et limitent les corps à8Kio. Aucune route HTTP ne permet de faire acquitter une preuve par un booléen. Le registre global est sauvegardé et restauré avec les données Moli.

Ce qui reste non qualifié ou non implémenté

  • Neutralisation HA réelle : aucune config entry n’est modifiée par le compagnon. Son observateur fiable n’est pas branché par défaut ; le statut quiescence_not_proven bloque la bascule.
  • Automatismes, scripts et scènes : pas d’import actif, pas de réécriture des références existantes ni de transfert du moteur. La provenance structurée préparée reste celle d’un brouillon inactif.
  • Identités HA existantes : les proxies ont leurs propres identifiants stables ; leur adoption dans les anciens automatismes est un jalon distinct.
  • Matériel : aucune box réelle ni pièce habitée n’a reçu d’ordre pour cette qualification. Une cible neutre et une validation encadrée restent nécessaires.
  • Exploitation continue : les files sont bornées ;256reçus par session sans éviction silencieuse. Le renouvellement et la charge prolongée de ce nouveau pont restent à qualifier.
  • Déploiement : le compagnon n’est pas installé sur les deux HA, et le nouveau module n’est pas activé dans le POC1414. Les services existants n’ont pas été redémarrés.
  • Fraîcheur : disponibilité du lien et état rapporté par HA ne prouvent pas la fraîcheur physique d’un retained. Aucun retour RTS n’est fabriqué à partir d’un acquittement.

Il s’agit du premier jalon de construction et de qualification simulée. Ce dossier ne présente pas le pont complet de migration comme déployé ou la reprise des automatismes comme achevée.
