Catalogue mémoire / V2

Le catalogue commun est intéressant ; les 96 octets partout ne sont pas obligatoires.

Un seul espace d’ID pour les équipements, valeurs et actions simplifie les liens et les recherches. Le banc montre le prix exact de cette simplicité, en séparant la ligne logique de son rangement physique.

Proposition : conserver le catalogue et les identités communs ; retenir provisoirement les lignes 64 o avec extensions numériques.

Sur la forme développée des deux exports, le catalogue mesuré demande 1 975 659 o · 1.884 Mio, contre 2 320 683 o · 2.213 Mio avec les lignes de 96 o. Économie : 345 024 o · 0.329 Mio, soit 14.9 % du périmètre mesuré. La variante en colonnes a le même coût de données et se choisit selon les accès mesurés ci-dessous.

Si les bornes doivent absolument être inline pour chaque objet, le format 96 reste valide et simple ; il faut accepter ses cases inutilisées. Le choix proposé reste révisable selon les vrais schémas et les liaisons d’actions encore inconnues. Aucun code du moteur n’a été modifié.

Les corrections apportées à l’analyse précédente

  • Une référence d’annuaire n’est pas un ID stable stocké dans la ligne. Le nouveau format contient un vrai id u64 et un parent u64. Un ID local est unique dans le catalogue ; l’identité entre installations est le couple installation128/local64, pas un u64 présenté comme universel.
  • Les 918 services ne sont pas 918 actions par équipement. Le banc les garde comme contrats partagés. Un scénario séparé ajoute quatre liaisons matérialisées par entité pour mesurer cette sensibilité ; il s’agit d’une hypothèse, pas d’un inventaire découvert.
  • has_set n’a pas été prouvé par les exports. 357 états sont candidats selon leur domaine et la présence de services usuels ; ils portent aussi ACCESS_UNRESOLVED. Ce bit ne devient jamais une permission. Sans preuve positive, l’interface ne doit pas annoncer un set disponible.
  • Les anciens totaux étaient des produits de tailles et un modèle partiel. Le nouveau banc mesure réellement les allocations vivantes des tableaux, l’index ID, les liens parent/enfants et un pool de taille mesurée. Cela reste un prototype, pas le RSS de Moli complet.
  • Les dates amont ne suffisent pas. Les 2 264 états exportés portent last_updated, sans last_changed/last_reported ; ni ces trois dates ni leurs cadences ne sont reconstituées. Les tests emploient trois dates synthétiques pour vérifier leurs rôles.
  • Une chaîne numérique peut rester du texte. Le préparateur V2 conserve text/input_text et les formats civils en texte ; les types sensor restent une observation, jamais une déclaration complète.
  • Une case peut disparaître sans que son identité soit réemployée. Le compteur d’ID refuse les reculs et débordements. La publication atomique de sa persistance et la reconstruction réelle après crash restent à implémenter.

Les exports n’exposent pas unique_id dans les entrées étudiées ; les chaînes opérationnelles comptées par la V1 ne prouvaient pas une identité native stable. 13 états actifs manquent au registre et 147 n’ont pas d’équipement lié : ne pas inventer leur parent.

Le schéma du banc utilise des références stub, toutes à zéro : les 918 contrats ne sont pas réellement résolus ni consultés. Le scénario liens4 ne distingue pas non plus quatre contrats exécutables ; il mesure seulement le coût de quatre fiches ciblées. Il ne teste pas un interpréteur de schémas. Les slots du banc sont immuables ; suppression et compaction du catalogue ne sont pas implémentées. La séparation ID/slot n’impose pas un HashMap : une table directe ou paginée serait une autre option, avec tombstones et borne de croissance à comparer. Elle n’a pas été mesurée ici.

Chaque essai donne la médiane de sept passages après chauffe, puis le rapport prend la médiane des trois essais séparés. Environ un million d’accès pré-calculés par passage ; leur génération reste hors chronométrage. Les snapshots mesurent allocation + copie + libération des tableaux et extensions, hors index et pool. Les mises à jour de texte/record imposent un handle immuable ou versionné (changement de handle testé, contenu du pool non interprété) : une mutation cachée sous le même handle ne serait pas détectée. Les lectures scalaires et mutations incluent les booléens/entiers/flottants, ainsi que la santé synthétique des équipements. Les accès payload/flags peuvent favoriser un format différent de la lecture des trois dates ; le détail brut contient également les mises à jour sans changement et le parcours des enfants.

Ce banc ne mesure pas verrouillage, transport, garde, abonnés, journaux, disque, rebuild de schéma ni commandes physiques. Les différences de nanosecondes dépendent du CPU et de ses caches ; aucune extrapolation à un Raspberry Pi ou au budget API p95 n’est faite.

Le processus de banc conserve une copie de référence de la charge, absente du futur catalogue unique. Le delta des pages anonymes à la construction est montré comme observation complémentaire ; pages, rétention de l’allocateur et bruit peuvent le distinguer des octets demandés. Le plafond de ce banc est 512 Mio pour permettre la fixture ×100 ; il ne modifie pas le budget produit de 32 Mio anonymes. À ×10, le catalogue doit encore laisser de la place aux transports, tâches, exécutions, caches, sécurité et autres composants. Un catalogue inférieur à 32 Mio ne prouve pas que Moli complet le sera.
