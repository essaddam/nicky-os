## 0. Méthode, preuves, limites

- **Lu par moi** : `crates/moli-runtime/src/{driver,orders}.rs` en entier et `hub.rs` pour le chemin d'un ordre (`command`, `prepare`, `send`, `Delivery`) : le contrat réel d'un pilote ; la V7 citée ci-dessus ; les crates `moli-overkiz` et `moli-roborock` en entier (sauf tests), leurs paquets `integrations/` et notes `.agentsroom/memory/features/`.
- **Lu par huit sous-agents** (sonnet-std, un lot chacun : cloud, MQTT/poussée, LAN, médias, réseau/machines, briques calculées, accès/alarme, profils) : toutes les autres crates, avec leurs `integrations/<id>/README.md` et notes de mémoire. Rapports bruts des sous-agents : non publiés.
- **Revérification** : j'ai relu une quarantaine de citations `fichier:ligne` prises au hasard dans tous les lots (ariston, nuki, z2m, philips, host, reolink, landroid, tapo, sonos, twinkly, phones, profile, core, hue, tuya, samsung, bambu, frigate, moonraker, esphome, telegram, presence, ipp, alexa, reservations, timers, asuswrt) : aucune erreur de ligne ni de sens. Les autres citations sont celles des sous-agents.
- **Notation** : « lu » = constaté dans le code ou la doc citée ; « jugé » = interprétation ; « non vérifié » = rien dans le dépôt. Chemins relatifs à `crates/<crate>/src/` dans les tableaux, sauf chemin complet.
- **Limites** : la plupart des pilotes n'ont jamais parlé à un vrai appareil (jalon H1) : fixtures reconstruites (Overkiz, Roborock, Ariston, Voltalis, Landroid, Twinkly, Nuki, Samsung…). Les latences, quotas et durées de jeton ci-dessous viennent du code, jamais d'une mesure. `docs/components/pilotes.md:853-889` ne donne comme vérifiés sur du vrai matériel que frigate, host, hue, igd, ipp, moonraker, philips (en lecture), reolink, sonos, telegram, tuya (local), z2m et quelques profils ; ariston, asuswrt, bambu, cast, huawei-lte, landroid, netatmo, nuki, overkiz, roborock, tapo, twinkly, voltalis et samsung n'ont que des contrats synthétiques ou des fixtures reconstruites.
- **Vocabulaire des issues** : le résumé de la mission en compte 7 ; la V7 §5.6 en compte 9 (elle ajoute `echec` : l'appareil ou le pont dit non, et `retenue` : la garde attend un humain) ; le kit esquissé en V7 §5.3 (l.368) liste encore les 4 anciennes (« confirmé, envoyé non confirmé, non remis, refusé ») : incohérence interne de la V7 à corriger.

## 1. Verdict

Bilan du grand tableau (58 lignes, §3) : **12 couvertes** telles quelles, **31 avec réserves** (la lecture et l'action tiennent, des détails du kit ou de la méta manquent), **6 mal couvertes** (philips, host, minuteries, luminaires, réservations, alarme), **9 hors modèle « module »** (briques propriétaires du hub, canaux privés, cache REST, bibliothèques).

1. **Lecture** : le contrat couvre toutes les intégrations (valeurs scalaires courtes : sondage, poussée, SSE, MQTT). Les réserves sont transversales et peu coûteuses : valeur inconnue (G5), santé (G6), texte en octets (G10), énumérations (G11).
2. **Action** : la grille « retour d'état » de la V7 (`etat`, `pont`, `accuse`, `aucun`) range bien les intégrations qui reçoivent des ordres (27 pilotes réseau, plus helpers, démo et luminaires). Quatre trous la fragilisent : l'appui n'est pas distinguable d'une consigne (G2), la confirmation passe souvent par un autre point ou un ensemble de valeurs (G3), le suivi après l'échéance n'a pas de règle (G1), un ordre composé ou adressé à un appareil éteint contredit « une seule fois » et « refus prédictif » (G13, G14).
3. **La phrase « le contrat couvre toutes les intégrations du dépôt, à quatre ajouts près » (V7 l.751-753) est trop forte.** Le crible trouve 26 écarts (G1 à G26) ; sept sont structurels :
   - G4 : l'isolation par processus (V7 §9.4.2 : « le contrat ne change pas ») est fausse pour les modules qui utilisent le coffre, l'attente humaine, les images, les passerelles HTTP partagées avec l'API : 24 des 37 genres de pilotes lisent le coffre, 15 y écrivent, 27 appellent `wait_for` (comptage du §5) ;
   - G7 : secrets et URL d'autorisation sur le bus ou dans le journal (codes de clavier Z2M, `sign_in` Alexa, position des personnes) ;
   - G2 et G3 : appui contre consigne, confirmation par code de commande ;
   - G1 : règle du suivi après l'échéance ;
   - G18 : les briques « propriétaires hub » (aides, minuteries, compteurs, calculs, scènes) ne sont pas des modules ;
   - G8 : appareils qui appellent Sarah Home (téléphones, agents de PC) ou qui tirent leurs ordres (boîte à lettres de `host`).
4. **Overkiz** (§6) : le pilote n'est pas « RTS bien géré, io à ajouter » : c'est « RTS géré, mais l'issue `execute` n'existe pas encore (COMPLETED et accepté sont le même `Ok`), le succès tardif n'est jamais dit, et io demande cinq changements de code et quatre précisions du contrat (retour par code de commande, confirmation qui attend l'arrêt du mouvement avec tolérance, consigne et appui dans une même voie, issue tardive nominale) ».
5. **Roborock** (§7) : couvert par `accuse` → `accepte`/`confirme`, à condition de G3 (confirmation sur `state`, ensemble de valeurs), G1 (fenêtre de suivi, erreur tardive), G2 (`control` est un appui). Les cartes n'existent pas dans le code.

## 2. Légende du grand tableau

- **Lecture** : `S n s` sondage de période n ; `P` poussée ; les occurrences sont écrites en toutes lettres ; entre parenthèses, l'origine.
- **Actions** : `[C]` consigne idempotente ; `[A]` appui ou impulsion ; `[L]` tâche longue ; `[S]` commande sans retour ; `[Ø]` aucune. `Control`/`Lock` = sémantique de garde (`spec.rs:245-252`, `hub.rs:1116-1127`).
- **Retour** : `oui` / `partiel` / `non`, puis ce que veut dire `reply(Ok)` aujourd'hui (`driver.rs:224` : « remis à l'appareil », jamais « fait »).
- **Issues** : `C` confirmé ; `X` exécuté par le pont (ou par l'appareil, pour un appui) ; `A` accepté ; `E` envoyé non confirmé ; `N` non envoyé ; `P` peut-être parti (`incertain`) ; `R` refusé ; `F` échec (V7 `echec`) ; `T` retenue (garde : tout point `Control`/`Lock` pour un agent). `tard` = issue tardive nécessaire (après les 5 s).
- **Couverture** : `couvert` (aucune extension propre à l'intégration) ; `réserves (G#)` (lecture et action tiennent, des détails du kit ou de la méta manquent) ; `mal couvert (G#)` (il faut une extension de structure) ; `hors modèle` (ce n'est pas un module api-to-mqtt : brique propriétaire du hub, canal privé, cache REST).
- Les sondages ci-dessous sont **les périodes du code**, pas celles de la V7 §5.9 quand elles diffèrent (voir §9).

## 4. Les cas mal couverts, et l'extension minimale de chacun

Gravité : **haute** (le contrat perd une garantie ou un secret, ou ne peut pas exprimer l'appareil), **moyenne** (se contourne dans le module mais chaque module le fera autrement), **basse** (règle à écrire). « V7 » = ce que `isolation-reactivite-runtime-v7.md` dit déjà.

### G1. Suivi après l'échéance : le canal existe, la règle manque (haute)
- **Constat.** Au moins 17 intégrations ont une suite après les 5 s : Ariston (relecture ≥20 s, suivi 180 s : `lib.rs:41,47`), Voltalis (120 s), Landroid (60 s : `lib.rs:44`), Nuki (+3 s puis +6 s, 30 s : `lib.rs:31-32`), Overkiz (120 s : `follow.rs:24`), Philips (réveil 45 s `lib.rs:26`, appli 60 s `android.rs:28`), host (WoL 10-60 s, arrêt ≥35 s, `remote` 15 min), Samsung (≤30 s), annonce Sonos (≈50 s), `say` d'ESPHome et de Reolink, push de phones (15 s), impression IPP (15 min), alarme (sortie 60 s), luminaires (≤15 s), scènes (≤30 s), `sign_in` d'Alexa. Aujourd'hui trois pratiques ad hoc : silence (Philips `lib.rs:463`), notice texte `MediaPublisher::tell` (Ariston `lib.rs:406,418`, Twinkly `runtime.rs:245-247`), journal.
- **V7.** Une issue rendue une fois avant l'échéance ; la suite est publiée une fois sur `evt/<appareil>/<point>` avec `{"id","i","tard":true}` (l.485-488).
- **Manque.** (a) La durée maximale du suivi, qui varie de 30 à 180 s selon le pilote. (b) Une API de kit pour conclure : `Ordre::repondre` consomme l'ordre (l.515-519). (c) Le cas `incertain` qui se révèle réussi : Overkiz suit par clé un ordre resté sans identifiant d'exécution mais ne dit jamais son succès (`follow.rs:199-210,238-240` : seul l'échec produit un `Outcome::Tell`) ; Ariston relance un suivi sans appelant (`lib.rs:388`). (d) Module mort pendant le suivi : l'ordre reste `accepte` pour toujours. (e) Le journal : l'observateur n'écrit que l'issue finale (V7 §20.7) ; il faut une seconde ligne. (f) Piège de déduplication : si la valeur demandée égale la valeur courante, rien n'est publié sur `in/` (V7 l.325) ; seule la lecture brute du module le prouve. V7 §8.2 étape 4 laisse croire que le hub juge `confirmé` sur `val/` ; le kit donne la main au module : à trancher dans le sens du module.
- **Extension minimale.** Méta du point écrit : `suivi_s` (≤180). `Ordre::conclure(issue, cause)` appelable une fois après `Accepte` ou `Incertain`, dans cette fenêtre. Le hub publie l'`evt` tardif, écrit la seconde ligne de journal ; à l'expiration sans conclusion, il publie lui-même `envoye` (ou garde `incertain`). Règle écrite : le module juge `confirme` sur la lecture brute, avant déduplication.

### G2. Appui contre consigne : la voie ne sait pas les distinguer (haute)
- **Constat.** `Kind::Button` n'accepte que `Null` (`spec.rs:369-370`) ; seuls Button, compteurs et minuteries sont des « opérations » avec `request_id` (`spec.rs:82-89`, `hub.rs:1043-1049`). Les appuis paramétrés sont donc des Enum, Text ou Binary : Overkiz `control` (`model.rs:153-160`), Roborock `control` (`model.rs:156-168`), Samsung `key`/`app`, Android TV `key`/`text`/`app`/`play_media`/`media_control`, Philips `key`/`media_control`/`text`, Cast `media_control`, Nuki `unlatch`, host `restart`/`sleep`, IPP `identify`/`cancel`, Landroid/Bambu/Moonraker `control`, `say`/`announce`/`notify`/`push`.
- **V7.** « Une consigne qui attend est remplacée par la suivante pour le même point ; un appui ou une impulsion n'est jamais remplacé » (§20.2, l.3218-3219) ; rien ne dit comment un module déclare un point appui.
- **Risque.** Trois `VolumeUp` fusionnés, deux annonces fusionnées, `stop` remplacé par `open`. Pire : la coalescence peut sauter par-dessus un appui : file `[position=30, stop, position=70]` ⇒ `position=70` part avant `stop`.
- **Extension minimale.** Méta par point écrit : `effet: "consigne" | "appui"`. La coalescence ne vaut que pour des consignes consécutives du même point, sans appui entre elles. Un point `appui` accepte la clé `k` d'idempotence sur `req/` (voir G18). Une consigne écartée rend `non_envoye` avec la cause `remplace` (V7 l.471 ne la liste pas).

### G3. Confirmation croisée, par ensemble de valeurs, et retour par code (haute)
- **Constat.** `Confirmations` n'attend que « même point, même valeur » (`orders.rs:209-253,337-342`). Cas réels : Roborock `control` → `state` (ensemble), Bambu, Moonraker, Landroid `control` → `state`, Nuki `unlatch` → `state` ∈ {5, 7} transitoire (`model.rs:180-189`), alarme `arm` → `state`, Philips réveil → `power`, Android TV volume et mute, Overkiz io `control` → `position` (pour `open` et `close` seulement : `stop` et `my` n'ont pas de cible).
- **V7.** `Retour::Etat { point }` (l.509) nomme un point, ni un ensemble ni un code. L'exemple de méta d'un volet io déclare `"retour": {"etat": "position"}` pour **les quatre codes** de `control` (l.556-562), y compris `stop` et `my`.
- **Extension minimale.** `retour` par **code** de l'énumération : `{"<code>": {"etat": {"point": "state", "attendu": [5, 6], "tol": 0}} | "pont" | "accuse" | "aucun"}`. Une valeur en mouvement ne se confirme qu'à l'arrêt (`mouvement` faux, ou deux relevés égaux) : passer par la cible en route n'est pas y arriver.

### G4. Services du module hors valeurs, et l'isolation par processus (haute)
- **Constat.** V7 §9.4.2 : le même module « tourne aussi dans un petit exécutable qui se connecte à l'écouteur local […] le contrat ne change pas ». Or (§5) 24 des 37 genres de `KINDS` lisent le coffre et 15 y écrivent (jeton à usage unique de Netatmo écrit avant usage, `actor.rs:251-260` ; épinglages TOFU de Hue, Philips, Samsung, Cast, Android TV, Sonos), 27 appellent `wait_for`, 8 la notice (`tell`), 7 `remove_device`, 14 relisent le cache du hub (`known_*`, `current`, adresse), 4 fournissent une image, 1 un document, 2 la voix, 5 partagent un `Arc` avec l'API (`main.rs:1093-1100`). Le kit V7 n'a que `declarer`, `valeur`, `evenement`, `vu`, `disponibilite`, `prochain_ordre` (l.351-364). V7 l.739-741 promet l'attente humaine sur `sys/` « avec un code de raison », sans appel de kit ; rien pour le coffre.
- **Extension minimale.** Nommer le **canal de services hub ↔ module**, hors courtier (appel direct en thread ; socket local authentifié en processus) : `secret`, `ranger_secret(…).await` (acquittement durable), `oublier_secret`, `attente(raison)` / `prete()` (publiés sur `sys/`), `retirer(appareil)`, `connu(…)` (appareils, clés, valeur courante, adresse), `images`, `document`, `media(ext, octets)`, `voix`, `entree_privee`, `fenetres`, `passerelle_http`. Règle : **un module qui monte une passerelle partagée avec l'API reste dans le processus du hub** (cast, androidtv, phones, host, netatmo). La V7 doit retirer « le contrat ne change pas » ou le conditionner à cette liste.

### G5. Valeur inconnue, inférée, silence normal (moyenne)
- **Constat.** `Value::Null` est publié sur un appareil **en ligne** par au moins 18 intégrations : Samsung UPnP absent (`queue.rs:94-97`), Android TV (`model.rs:28-34`), Cast (`driver.rs:36-50`), Hue `mirek:null` (`model.rs:590-593`), Twinkly (`runtime.rs:330-336`), Nuki (`model.rs:262-290`), Tapo `color_temp` 0 (`lib.rs:405`), Landroid (`model.rs:384-417`), Netatmo (`observed.rs:54-59`), asuswrt, netgear, huawei, reolink, ipp, moteur de profils (`profile.rs:233,1191`, `lib.rs:1237-1241`), minuterie invalidée, temporel incertain, calcul vide. La charge V7 §7.3 (l.940-947) ne connaît ni nul ni valeur inférée. Philips pose `power=false` quand la télé ne répond pas (`lib.rs:771-776`). V7 §10.5 dégrade en qualité mauvaise un appareil muet ; or télé en veille, ampoule coupée au mur, capteur sur pile, serrure sans rythme sont des silences **normaux**, et pour `presence`, `phones`, `personnes` le silence **est** le signal.
- **Extension minimale.** `v: null` = inconnu (qualité `m` par défaut, `u` posable par le module) ; une valeur inférée porte la qualité `u` ; `sante.veille` ou `rythme = None` ; le rythme appris (V7 l.1479-1483) ne s'applique jamais à un appareil dont le silence est le signal ; une sonde illisible rend `disponibilite(false)`, pas `home=false` (`presence/lib.rs:261`).

### G6. Santé : quatre trous (moyenne)
- **(a) `$vu` par appareil contre plusieurs sources ou rythmes.** Moteur de profils (Daikin 30/60/3600 s, Meross 15/3600, SMLIGHT 60/3600, Tempo 1800/3600), host (sonde 15 s + agent 5 s, `lib.rs:786-793`), routeurs (60/300/3600 s), Nuki (pont ≠ serrure), Hue (SSE ≠ `zigbee_connectivity`), Tuya (local ≠ cloud). Aujourd'hui la fraîcheur est par point (`hub.rs:2444-2454`) ; V7 l.332 : `$vu` « met à jour tous les points de l'appareil ».
- **(b) « Une réponse réussie compte comme une nouvelle » (V7 l.1433-1435) est faux** pour les API qui rendent la dernière mesure : Netatmo (une date répétée ne rafraîchit rien : `observed.rs:40-52`, `pilotes.md:542-543`), iopool `measuredAt`, Tempo, Open-Meteo `current.time`.
- **(c) Rythme plus court que la fenêtre `$vu`** (une minute, V7 l.325-326) : Sonos 2 s, Reolink 1 s, Overkiz 10 s ⇒ muet à tort.
- **(d) Pauses imposées par le cloud plus longues que `rythme × (pertes + 1)`** : Ariston 900 s contre 540 s, Voltalis 600 s contre 240 s (`lib.rs:49`), Landroid 1 h, Overkiz 60 s, Réservations TTL poll + 10 s (`runtime.rs:87-89`) ; requêtes d'une heure sans point (Daikin `basic`, Meross `all`, Moonraker `info`) qui retiennent « en ligne » 30 à 90 min (`profile lib.rs:809,821-825`) ; SMLIGHT à zéro perte.
- **Extension minimale.** `$vu` avec `p` (liste de points ou groupe) ; règle « nouvelle = horodatage source plus récent, sinon pas de `vu` » ; fenêtre `$vu` ≤ rythme ; le module publie `pause_jusqu_a` sur `sys/`, qui suspend l'échéance de silence ; `[sante]` dans le format de profil (G24).

### G7. Secrets et données sensibles sur le bus et dans le journal (haute)
- **Constat.** (1) **Codes de clavier Z2M** : aujourd'hui Mosquitto externe, puis canal mémoire privé (`moli-z2m/src/keypad.rs:7-26`, `driver.rs:557-567`) ; avec Z2M client du courtier de Sarah Home (V7 §15.1) le JSON portant `action_code` entre dans le courtier et dans son journal de filtre avant que le module ne le détourne : **régression d'une protection existante**. (2) **`sign_in` d'Alexa** : l'URL collée (elle porte un code d'autorisation) part par `/api/command` (`web/src/maison/ui/AlexaAccount.svelte:23-26`), donc par la garde et le journal (`hub.rs:973-976`) ; `private_value` ne regarde que les textes JSON (`privacy.rs:80-98`) ; avec V7 elle traverserait aussi `req/` et `cmd/`. (3) **Position** : latitude, longitude, précision, Wi-Fi sont des points ordinaires (`phones:*`, `personnes:*`), filtrés par noms de clés pour le LLM et par genre de pilote pour les invités seulement ; sur `val/#` ils iraient à l'archiveur, au module WebSocket, à la secours (aucun filtre MCP/historique trouvé : non vérifié). (4) **Textes de notification** (phones `push`, Telegram, annonce Sonos) : valeurs de points, donc dans le journal et sur `cmd/`.
- **V7.** §16 n'a pas de ligne « codes, PIN, jetons, URL d'autorisation ».
- **Extension minimale.** Règle : aucun code, jeton, PIN ni URL d'autorisation sur un sujet `moli/v1/*` ni dans une ligne de journal. Drapeau `sensible: secret | position | texte_prive` par point dans la méta (`secret` refusé par le kit). Crochet d'entrée dans le routeur du courtier pour les sujets de claviers déclarés au catalogue Z2M (même test `privacy::private_json`), sinon garder Z2M sur son propre courtier. Les flux humains avec secret (`sign_in`, OAuth) restent en REST du module, jamais en `cmd/`.

### G8. Appareils qui appellent Sarah Home ou qui tirent leurs ordres (haute)
- **Constat.** « Le module lit l'API de l'appareil » ne décrit pas : (a) `phones` : l'appli POSTe ses rapports (`phones.rs:111-146`) ; (b) `host` : l'agent du PC POSTe son rapport toutes les 5 s et reçoit ses ordres **dans la réponse** (`agents.rs:123-156`) ; la boîte garde l'ordre 15 min et le rejoue à chaque rapport jusqu'à `done` (`agents.rs:22,140-149`), alors que `done` veut dire « reçu » et non « fait » (`moli-agent.ps1:817-819`) ; la route `remote` n'est pas un point, hors garde `Control` et hors journal d'ordres (`machines.rs:94-130`) ; (c) les flux d'appairage à réponse : Netatmo (URL puis échange de code, 20 s : `gateway.rs:103-138`), Cast (activation, liste ≤64), Android TV (Polo, code de 6 caractères), Alexa `sign_in`. Ce sont des routes REST montées par l'API, partageant un `Arc` avec le pilote.
- **Extension minimale.** Règle de fiche : « module à entrée HTTP = passerelle dans le processus du hub ; l'API vérifie jeton, droits et quotas ; le module ne reçoit que des rapports bornés ». Appareil qui tire ses ordres : boîte propre au module, TTL par type d'ordre (5 à 35 s pour arrêt, redémarrage, veille ; 15 min seulement pour `remote`), issue `accepte` puis `evt` tardif à l'accusé, jamais « rejoué » depuis `cmd/`. `remote` devient un point `appui` à décision humaine (famille `Lock`).

### G9. Hors MQTT : trois enregistrements manquent au kit, et la méta est trop courte (moyenne)
- **Constat.** Images à la demande (Reolink `lib.rs:585`, Frigate `lib.rs:421-430`, Moonraker `lib.rs:182-188`, démo), documents (IPP `lib.rs:587-593`), audio et voix (Sonos `announce.rs:154-163`, ESPHome `satellite.rs`, Reolink `door.rs`), via `DriverCtx::provide_snapshots`, `provide_printing`, `media_publisher`, `voice_brain`. Leur accès passe par une garde différente de celle des ordres (pièce protégée → session humaine, `rest.rs:883-890` ; impression réservée au tableau de bord, `rest.rs:947-955`). ### G10. Tailles, retenus et clients extérieurs (moyenne)

### G13. Ordres composés : lecture-modification-écriture, émulation, bascule (moyenne)
- **Constat.** « Envoyer une seule fois » et « jamais de bascule » (V7 §5.1) face à : Daikin, trois GET (`lib.rs:862-866`) ; Landroid `schedule` (`model.rs:540-555`) ; Voltalis, réglage manuel entier (`model.rs:309-351`) ; Ariston, ancienne valeur renvoyée avec prérequis de relecture (`model.rs:351-368`, `lib.rs:622-654`) ; Android TV, volume émulé touche à touche (`execution.rs:82-137`) et mute par bascule conditionnelle avec course probable (`commands.rs:25-34`) ; Philips, mute = GET + POST (`lib.rs:634-644`) et touche Standby de repli qui **bascule** (`lib.rs:596-611`) ; Twinkly, relecture + 1-2 POST + relecture, jusqu'à 14 échanges pour 5 s (`runtime.rs:75,110,122`) ; Alexa `play`, 2 appels (`api.rs:174-192`).

### G14. Hors ligne n'est pas non commandable (moyenne)
- **Constat.** Le hub ne regarde pas la disponibilité avant d'envoyer (`hub.rs:1731-1787` : `prepare` et `send`) : le Wake-on-LAN de Samsung, de Philips et de host en dépend. V7 §20.2 (l.3195) « refusé sans attendre si le disjoncteur de l'appareil est ouvert » et l'issue « non envoyé : box hors ligne » (l.471, 595) vont dans le sens contraire pour un appareil qui dort. Android TV et Cast refusent tout ordre hors ligne (`androidtv-driver driver.rs:163-166`, `cast driver.rs:154`) : pas de réveil. Le commentaire de `host/src/lib.rs:735-736` (« un appareil hors ligne refuse l'ordre qui le réveille ») suppose un refus que je n'ai trouvé ni dans `hub.rs` ni dans `rest.rs:111-175` : à vérifier côté interface.
- **Extension minimale.** Attribut `reveillable` dans la méta : l'ordre passe vers un appareil hors ligne, issue `envoye` puis `evt` tardif à la réapparition ; le refus prédictif du disjoncteur vise le bus ou le module, jamais la disponibilité d'un appareil qui dort.

### G17. Fan-out et issue agrégée (basse)
- **Constat.** Telegram : 10 chats en série, le premier refus coupe (`lib.rs:208-213`) ; Alexa `say` répété pour chaque membre d'un groupe (`lib.rs:416-457`) ; luminaires : V7 dit « la moins bonne des membres » (l.700) alors que le code rend `Ok` dès **une** ampoule a obéi (`lights lib.rs:499-506`) ; scènes.

### G18. Briques propriétaires du hub (moyenne)
- **Constat.** Aides, minuteries, compteurs, bouton, dates, calculs, durées, plannings, scènes sont des **propriétaires dans `moli-runtime`**, avec dix méthodes de `DriverCtx` hors kit (`driver.rs:350-451`). Les passer par un module api-to-mqtt ferait un écho de cinq sauts (`req`, `cmd`, `in`, `val`, `res`) pour écrire sa propre vérité. Idempotence : `request_id` `client(32 hex):séquence` (`occurrence.rs:78-100`) ≠ `id` ULID de `req/` (V7 l.434) ; un doublon doit recevoir l'issue d'origine (`compteurs.md:44-49`). `finished` d'une minuterie est une livraison durable avec accusé et « consommateur prêt » (`timer_hub.rs:255-268`), pas un `evt/` QoS 1 sans rétention ; `remaining` coûte 1 message/s par minuteur actif. Sept fichiers métier (`backup.rs:32-38`) absents de la réplication V7 §18.2.
- **Extension minimale.** `proprietaire = hub` dans la méta (pas de sujet `cmd/` : le hub applique l'ordre, écrit `val/`, rend l'issue) ; `volatile` (`remaining` : ni archive ni déclencheur) ; `k` (clé d'idempotence) dans `req/`, doublon ⇒ issue d'origine republiée + bit « réessai sûr » ; les occurrences durables restent dans le hub ; ajouter les sept fichiers à la réplication.

### G19. Occurrences dérivées d'un niveau, et identité d'occurrence (moyenne)
- **Constat.** Seuls Hue (`lib.rs:303-304`) et réservations (`publisher.rs:164`) appellent `pulse_state`. Reolink : la sonnette est un niveau `alarm_state` interrogé à 1 s (`lib.rs:721-728`) : deux sonneries dans la fenêtre fusionnent, une sonnerie courte est perdue ; Z2M `action`, ESPHome `wake_word` (`satellite.rs:159-165`), Frigate (comptes), Hue `repeat` (battement de maintien). `evenement(appareil, point, v)` n'a pas d'instant observé (V7 l.358). L'occurrence du hub a identité, flux, position, corrélation, drapeau durable (`occurrence.rs:14-41`) ; la charge `evt/` de V7 §7.1 ne les décrit pas, et QoS 1 peut dupliquer.
- **Extension minimale.** `evenement(…, observe)` ; charge `evt/` = `{id: source:seq, c: corrélation, v, t}` ; le module dérive le front montant d'un niveau et déclare `source: niveau` et la résolution dans la méta ; doublon écarté par `id`.

### G20. Mort d'un module avec un ordre pris (moyenne)
- **Constat.** V7 l.2905 : « ses ordres en cours sont refusés ». Nuki NUK-R4-001 : une réponse absente après émission est « non confirmé », jamais « non envoyé » (`.agentsroom/memory/features/nuki.md`, `lib.rs:86-93`). Le superviseur d'aujourd'hui ne vide que la file (`pilotes.md:26-28`).

### G21. Permis vivant et révocation avant émission (basse)
- **Constat.** `CommandPermit` est une fermeture revérifiée jusqu'à l'émission (`driver.rs:44-60,110-153`) : invités (fin de séjour, réservation annulée, calendrier hors ligne : `people.rs:624-641`), scènes (`scene_execution.rs:358-362`), exécution d'automatisme annulée (`run.rs:145-148`). Sur `cmd/`, seule l'échéance voyage.
- **Extension minimale.** Échéance d'un ordre à permis = min(5 s, fin de la fenêtre) ; `cmd/<module>/$annule` portant l'`id`, lu par `abandonne()`. Risque résiduel borné à 5 s.

### G22. Fenêtres d'accès invité (moyenne)
- **Constat.** Registre éphémère module → hub : ≤4096 fenêtres (`reservations.rs:56`), TTL ≤3 610 000 ms (`reservations.rs:52`), double horloge, jamais restauré du cache, fermé quand le module cesse d'être `Running` (`hub.rs:2024-2026`). - **Extension minimale.** Appel en mémoire `fenetres(liste, expire_ms)`, hors courtier, ou ne publier que les ≤6 fenêtres utiles ; garder « fermé si le module n'est plus `Running` ».

### G23. Alarme (moyenne, spécification seulement)
- **Constat.** Désarmer, changer de mode, exclure, passer le délai portent un code et ne sont jamais des points (`alarme.md:79`) ; `req/<origine>` est `{id,p,v,a,e}` (V7 l.434) et `req/#` est lu par la secours ; `Origin` n'a pas de `keypad` (`event.rs:129-147` ; `Source::Keypad` n'existe que dans `moli-alarm`) ; `arm` a un effet différé (sortie 60 s) ; sirène et notification « partent quand même » (`alarme.md:337`) contre « jamais rejoué, 5 s ». Aucun pilote alarme n'existe (`config.rs:313` réserve le namespace).
- **Extension minimale.** Les ordres à code entrent par le canal privé (REST `POST /api/alarm`, `KeypadReceiver`) dans la file unique de l'alarme ; origine `keypad` (acteur = id du clavier) ; `suivi_s` sur `arm` (G1) ; pour les ordres critiques, le demandeur réémet sous un nouvel `id` tant que l'issue n'est pas `accepte`/`envoye`, budget borné.

### G24. Profils déclaratifs : le format cible (moyenne)
- **Constat** (lot G, table v6 §5.4 contre le format réel) : `scale` est un multiplicateur f64, pas un « entier à l'échelle » (`profile.rs:190-194,1196-1213`), et 30 des 73 numériques n'ont pas de `round` ; le libellé EST la valeur, ni code ni clé i18n (`profile.rs:184-189`) ; aucun champ pour l'instant observé ni la fraîcheur de la source ; santé non déclarable (pertes à 3 en dur, `lib.rs:43`) ; bornes `min/max/step` d'ordre seulement (`profils.md:94`) alors que V7 valide `in/` contre la spec ; pas de profil mixte GET + MQTT ; aucune lecture de `Retry-After` (iopool retente 4 fois plus vite après échec) ; **approbation non forgeable absente** : `moli-os profile trust` enregistre le hash aussitôt, sans question (`main.rs:827-852`, `trust.rs:15,44-53`), un agent avec un shell approuve son propre fichier, alors que V7 §19.2 suppose « un agent les écrit, un humain les valide ».
- **Extension minimale.** `observed_at = "<requête>.<chemin>"` par requête et `fraicheur_s` par point ; `[sante]` (rythme, pertes, important), une requête sans point ne compte pas ; table `code ↔ brut(s) ↔ clé i18n` par point, dont dérivent lecture et écriture ; `round` obligatoire pour un numérique ; bornes d'ordre distinctes des bornes de validité ; geste d'approbation authentifié (PIN) avec affichage des `map` ; budget d'appels et `Retry-After`.

### G25. Module = instance, pas genre (basse)
- **Constat.** `Module::nom()` est un `&'static str` par module (V7 l.347) alors que le code a plusieurs instances d'un même genre (helpers, démo, profile ×8, Hue par pont) et confine par instance (`driver.rs:612-614`).
- **Extension minimale.** `<module>` de `in/<module>/#` = id d'instance, comme aujourd'hui.

### G26. Valeurs à variation permanente (basse)
- **Constat.** `uptime` (igd `lib.rs:363-365` : 6 msg/min), débits (asuswrt `rx_rate`, host `net_*`), `remaining` des minuteries (1 Hz), `media_position` Cast (~10 s) : la déduplication n'économise rien ; host arrondit à la minute, igd non.
- **Extension minimale.** Règle « quantifier les durées croissantes » + drapeau `volatile` (G18).

### 6.3 RTS (sans retour) : ce que le contrat demande

Le pilote est déjà la forme du contrat : une voie, une émission, jamais de position supposée (`read:false`). Quatre ajustements, tous dans le pilote et dans la méta :

1. **Séparer `execute` de `accepte`** dans la réponse (aujourd'hui `Due::Accepted` et `Outcome::Answer(Ok)` donnent le même `Ok`).
2. **Dire le succès tardif.** `Tracker::taken` et `moved` ne produisent un `Outcome::Tell` que pour un échec (`follow.rs:205-208,240`). Un ordre cloud resté sans identifiant d'exécution (`Unanswered` ⇒ `Err(box_muette)`) peut aboutir en réalité : la famille a lu une erreur et le volet s'ouvre. La V7 le règle par l'`evt` tardif (G1), à condition qu'il porte aussi le succès.
3. **Déclarer `control` comme `effet = appui` et `retour = pont`** (G2) : `open` puis `stop` ne doivent jamais être fusionnés ni inversés (la mémoire `overkiz.md` rapporte que des tâches indépendantes inversent « open » et « stop » avec le cloud). La file FIFO du pilote le garantit aujourd'hui ; la voie générique du kit doit le savoir.
4. **Garder la sémantique de garde dans la méta** (G9) : `Other` pour le portail, `Control` pour les autres machines au travail ; la V7 §5.7.1 (l.551-554) ne la montre pas.

Verdict RTS : **couvert** (G1, G2, G9).

### 6.4 io-homecontrol (avec retour d'état) : ce que le pilote ne fait pas, et ce qu'il faudrait

Le pilote ne supporte aucun appareil io. La V7 l'admet (« les classes io ne sont pas encore publiées […] parce qu'aucune n'a été observée », l.617-619). Ce qu'il faudrait, point par point, avec l'endroit du code :

| Besoin | Où | Détail |

| Un point `position` | `model.rs:142-201` (`points`) | Numeric 0-100 `%`, lu si `core:ClosureState` est déclaré, écrit si `setClosure` l'est ; éventuellement `mouvement` (Binary, `core:MovingState`). | Lire la position | `model.rs:277-309` (`decode`) | `core:ClosureState` (0 ouvert, 100 fermé selon V7 §5.7.3) → `100 − fermeture`, en entier ; le cloud envoie des nombres en texte (`"42"`), déjà géré pour l'intensité (`model.rs:291-294`). |

Ce que le **contrat** doit en plus (au-delà de V7 §5.7.3) :

1. **`retour` par code de commande, pas par point.** L'exemple de méta V7 (l.556-562) déclare `"retour": {"etat": "position"}` pour `control`, donc pour `open`, `stop`, `my`, `close`. `open` et `close` ont une cible (100 et 0 en canon) ; `stop` et `my` n'en ont pas (le moteur s'arrête où il est ; la position favorite est dans le moteur et inconnue du module) : leur meilleure issue est `execute`. → G3.
2. **Une valeur en mouvement ne se confirme qu'à l'arrêt.** Une consigne à 50 lancée depuis 0 passe par 50 en route : comparer le dernier relevé à la cible (`Confirmations::same`, `orders.rs:337-342`) confirmerait trop tôt. La conjonction correcte est `COMPLETED` (ou `mouvement` faux) **et** `|position − cible| ≤ tolérance`.
3. **Une consigne `position` et un appui `control` dans la même voie.** Les `setClosure` successifs se coalescent (dernière consigne gagne) mais jamais par-dessus un `stop` en attente (G2).
4. **Issue tardive pour le cas nominal.** Un io met une vingtaine de secondes : `accepte` à 4,6 s, puis `evt` tardif `confirme` ou `echec`. La fenêtre de suivi (`suivi_s`) doit couvrir le trajet complet (120 s existent déjà dans `follow.rs:24`). → G1.
5. **Non vérifié** : si `COMPLETED` signifie « le moteur a atteint la position » ou « le moteur a accusé l'ordre ». Aucune box réelle n'a été vue (fixtures reconstruites, `integrations/overkiz/README.md` « Deviné »). Le plan de la V7 repose sur la première lecture ; la qualification H1 doit la mesurer avant de figer l'issue de `control` sur io.

Verdict io : **réserves fortes**, pas de trou de structure : le suivi par exécution existe, il manque la cible, la tolérance, le retour par code et le chemin de succès tardif.

### 6.5 Overkiz et le reste du contrat

- **Voie** : une file pour toute la box, justifiée par l'ordre d'arrivée sur une API HTTP (le cloud ouvre une connexion par requête). La voie V7 est par appareil ; la clé de voie doit être choisie par le module (G15).
- **Cloud contre local** : le Connectivity Kit n'a pas d'API locale ; les classes OGP passent par le cloud, 30 s au repos et 2 s en suivi. Avec 10 s de limite de requête cloud (`api.rs:36`) et une réponse due à 4,6 s, `Unanswered` (aucun identifiant d'exécution à l'échéance) est un cas réel dès que le cloud est lent, d'où l'importance du succès tardif (jugé : aucune latence réelle mesurée).
- **Session cloud** partagée entre redémarrages, générations de session, 3 refus ⇒ attente humaine (`api.rs:108-140`, `lib.rs:60`) : services du hub (G4).
- **Rythme** : relevé de la box = battement ; un relevé réussi doit publier `$vu` pour chaque appareil de la box (V7 l.544) ; `rythme` 10 s, 2 pertes, mais pause cloud de 60 s (G6).

### 7.3 Ce qui manque au contrat pour ce robot

1. **Confirmation sur un autre point, par ensemble de valeurs** (G3). `control = start` se confirme sur `state`, parmi plusieurs codes. `Confirmations` ne sait pas (`orders.rs:209-253`). Même cas : Bambu, Moonraker, Landroid. À écrire dans la méta de `control` : `retour` par code, avec l'ensemble attendu.
2. **Fenêtre de suivi et erreur tardive** (G1). Un robot qui accepte `start` puis annonce `error = dust_bin_missing` ou `stuck` quelques secondes plus tard : aujourd'hui personne n'est prévenu **de l'ordre** (l'état et l'erreur changent, c'est tout). Il faut `suivi_s` (60 s existent déjà comme `FOLLOW_FOR`, `lib.rs:36`) et un `evt` tardif `echec` portant le code d'erreur. Une panne qui survient 20 minutes plus tard n'est pas l'échec de l'ordre : c'est une valeur (`error`), et le workflow la lit sur `val/`.
3. **Le retour à la base est une attente de workflow, pas l'issue de l'ordre** (V7 l.652-656, correct) : `home` rend `accepte` puis `confirme` quand l'état change ; « à la base » = `wait_for state ∈ {charging, charging_complete}` avec un bail durable. Le moteur n'interroge jamais le robot.
4. **`control` est un appui** (G2) : `pause` puis `stop` ne se fusionnent pas, `start` ne remplace pas `home`.
5. **Codes natifs** (G11). Les 23 états et 28 erreurs ont déjà un code du fabricant : c'est le code canon. `names()` dédoublonne les **libellés** (`model.rs:131-140`) : les codes d'erreur 15 et 26 portent le même libellé `wall_sensor_dirty` (`model.rs:59,69`), ce qui perdrait une distinction si le libellé servait de clé. `clean_time` et `clean_area` passent de `Float` à entier d'échelle 1 (dixièmes).
6. **Rythme variable** (G6) : 30 s au repos, 5 s au travail. Le module déclare 30 s et deux pertes (muet à 90 s), ou re-déclare la santé en activité. `wait_for(injoignable)` double déjà `set_online(false)` (`lib.rs:405,444,453`) : ce n'est pas une action humaine, il doit disparaître au profit de `disponibilite(false)` seul.
7. **Pas de réveil ni de redécouverte** : l'adresse est donnée par un humain (bail fixe) ; un changement d'adresse ⇒ `autre_appareil` (G4 : `known_address`, `wait_for`).
8. **Appairage et jeton** (G4) : le jeton (32 hexa) est extrait de Mi Home par le propriétaire et rangé au coffre ; il change si le Wi-Fi de l'aspirateur est réinitialisé. Services du hub, pas des valeurs.

### 7.4 Les cartes et les zones

Rien n'existe, donc rien ne bloque le contrat. Si le pilote les ajoute :

- la **carte** est une image : elle passe par l'enregistrement d'images à la demande du kit (aujourd'hui `provide_snapshots`, conçu pour les caméras : `driver.rs:477-485`), jamais par MQTT (V7 §16, l.2375) ; ce n'est pas seulement un JPEG (pièces, zones, position du socle, trajet) : la structure est un document servi par REST ;

## 9. Écarts entre la V7 § 5.9 et le code

Chaque ligne : ce que dit la V7, ce que fait le code.

1. **l.726 « HTTP ou SOAP par cycles de 30 s »** (asuswrt, netgear, huawei-lte) : la période est de 60 s (asuswrt `config.rs:27-35`, netgear `lib.rs:44-52`, huawei-lte `config.rs:37-42`) ; 30 s est le budget d'un cycle (asuswrt `runtime.rs:115-120`).
2. **l.742-743 « catalogues qui bougent (Zigbee2MQTT, Hue, Tuya) »** : le catalogue de Tuya est lu une fois (`tuya lib.rs:105-117`) ; un ajout demande un import et un redémarrage.
3. **l.691 Tapo « le relevé suivant »** : le prochain relevé tombe à 5 s au pire, au plus tard à l'échéance ; le code publie aujourd'hui la valeur demandée (`tapo lib.rs:675-678`). Il faut une relecture juste après l'écriture, dans la même session.
4. **l.692 Sonos « une annonce est `execute` »** : c'est `accepte` puis un `evt` tardif (voix ≤30 s + clip ≤20 s : `announce.rs:99-136,229-262`) ; et « le relevé » est aujourd'hui un écho optimiste (`sonos lib.rs:381-385`).
5. **l.693 et l.711** : le paquet Wake-on-LAN est `accepte` pour une télé (l.693) et `envoye` pour `host` (l.711). Une trame UDP sans accusé est `envoye` dans les deux cas.
