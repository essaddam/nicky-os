Ce qui tombe,ce qui tient.

Un pilote qui panique est isolé et relancé sans que la maison le remarque. Un pilote qui bloque, qui se tait ou qui traite tout à la file, une brique qui panique, une faute de processus ne le sont pas encore. Lecture du cœur et de 45 crates, huit expériences contre le vrai code, et un plan court pour fermer ces brèches.

Date : 21 octobre 2026. Statut : analyse, aucune modification du code. Base analysée : main au commit d0ce806. Les exemples sont fictifs.

Périmètre : 57 crates, environ 125 000 lignes de Rust hors tests (160 000 avec). Le cœur (moli-runtime, moli-os, moli-api, moli-automation, moli-history, moli-net) a été lu en détail. Les 45 crates de pilotes et de briques ont été lues selon une même grille (trois relectures parallèles), et chaque constat de gravité élevée a été revérifié dans le code. Huit expériences ont été exécutées contre le vrai moli-runtime et la vraie version de roxmltree, dans des crates jetables hors du dépôt (annexe A). Les décisions de l'architecture (D0 à D13) sont tenues pour acquises.

1. Réponse courte

Oui pour les paniques des pilotes, pas encore pour le reste. Le cœur sépare bien les pilotes entre eux : un pilote qui panique est capturé, relancé avec une attente croissante, ses ordres en attente sont refusés et ses appareils passent hors ligne ; le reste de la maison ne voit rien (E1 : 3 paniques en 3,5 s, 156 ordres sur 156 servis pendant ce temps, médiane 0,06 ms).

Mais « planter » prend plusieurs formes, et le superviseur n'en attrape qu'une :

Défaillance d'un module Effet aujourd'hui Preuve Gravité
Panique dans Driver::run Isolée, relancée (1 s → 60 s), statut public E1 Maîtrisé
Appel bloquant ou calcul long sur un worker Un seul : absorbé par le second worker. Deux : toute la maison avance par pas de ~200 ms. Une réponse XML hostile de 1 Mio occupe un worker 96,6 s E2, E8 Élevé
Pilote figé, ou « prêt » avant d'être connecté Reste running pour toujours ; chaque ordre échoue au bout de 5 s ; jamais relancé E3 Élevé
Panique dans une brique (moteur d'automatismes, historique, énergie, horloges) La brique meurt en silence, rien ne la relance, /api/health reste vert E4 Élevé
Appareil lent derrière un pilote qui traite tout à la file Les autres ordres du pilote expirent ; pour le pilote des luminaires, toutes les lumières de la maison attendent lecture du code Élevé (luminaires), Moyen ailleurs
Ordre émis après que l'appelant a renoncé L'appelant lit « délai dépassé », l'appareil agit quand même, et après l'échéance le journal dit aussi « délai dépassé » (9 pilotes) lecture du code Moyen
Faute de processus (débordement de pile, mémoire, abort) Tout le processus s'arrête (code 134) ; Docker relance ; boucle possible si l'entrée fautive persiste E7 Moyen (aucun cas trouvé)
Erreur à la construction d'un pilote (fichier de données illisible) Toute la maison refuse de démarrer lecture du code Moyen

Réactivité. Le cœur est très rapide et bien découplé : environ 100 000 ordres aller-retour par seconde sur la machine de test, un abonné lent ne freine personne (E5), le verrou global du modèle n'est pas un goulot à l'échelle d'une maison (E6). Les risques de latence sont aux bords : deux workers seulement, des pilotes qui font leurs entrées-sorties dans leur boucle de commandes, et un moteur d'automatismes qui traite tous les événements à la file, écritures disque synchronisées comprises.

Pilotes et services tiers. La grille est rassurante sur l'essentiel : aucun std::thread::sleep, aucun std::net synchrone, aucun canal non borné, des tampons toujours plafonnés, des décodeurs qui vérifient avant d'indexer, pas de récursion sur des données réseau. Les défauts sont des défauts de forme, répétés : entrées-sorties dans la boucle de commandes, garde d'abandon pas toujours appliquée, quelques sous-tâches lâchées, deux pilotes qui se déclarent prêts avant d'être connectés, un décodeur XML au coût quadratique.

Optimisation Rust. La base est saine et sobre : identifiants Arc<str>, bus broadcast à valeurs partagées, files bornées, SQLite hors des workers, unsafe interdit dans les 57 crates, LTO complète. Les gains restants sont petits et localisés : allocations évitables sur le chemin le plus chaud du hub, balayages linéaires et horloge à 1 Hz dans le moteur d'automatismes, images de caméra copiées trois ou quatre fois.

2. Ce qui protège déjà la maison

2.1 Le superviseur des pilotes

  • Chaque pilote tourne dans sa tâche ; catch_unwind enveloppe run (crates/moli-runtime/src/supervisor.rs:38). Un retour Ok ou Err est traité comme une panne.
  • Attente de 1 s doublée jusqu'à 60 s, remise à 1 s après 60 s de bon fonctionnement (supervisor.rs:16-19, 45-47).
  • À chaque panne : file d'ordres vidée (drain, l. 50), appareils hors ligne (l. 51), statut Backoff { error, retry_in_ms } publié sur le bus (l. 53-59).
  • Le même DriverCtx survit aux relances (l. 28-29) : la file n'est jamais recréée, aucun ordre ne tombe dans un trou pendant le redémarrage.
  • panic = "unwind" est gardé volontairement en release (Cargo.toml:129) : sans lui, catch_unwind ne servirait à rien.

2.2 Le contrat d'un ordre

  • File par pilote bornée à 64 ordres (hub.rs:59), remplie par try_send : une file pleine répond Busy tout de suite, l'appelant n'attend jamais (hub.rs:1807-1825).
  • Échéance de 5 s portée par l'ordre (hub.rs:115, 1806). Un ordre périmé n'est jamais remis au pilote (driver.rs:574-586) ; le pilote peut revérifier juste avant l'émission (CommandRequest::abandoned, SendPermit::begin_send, driver.rs:136-190).
  • Prise ou abandon tranchés par un seul compare_exchange sur un AtomicU8 (driver.rs:96-108) : un ordre est pris ou abandonné, jamais les deux.
  • Exactement une ligne de journal par ordre, même si l'appelant disparaît (Observer, Delivery et leurs Drop, hub.rs:354-424).

2.3 Le bus et le modèle

  • Bus tokio::sync::broadcast de 1 024 événements (hub.rs:114, 583). Un abonné lent reçoit Lagged(n) au lieu de freiner les autres ; le SSE et l'historique se resynchronisent par un instantané (moli-api/src/sse.rs:128-131, moli-history/src/lib.rs:343-352).
  • Un état n'est émis que s'il change (hub.rs:2416).
  • Identités et valeurs partagées à coût constant : DeviceId et PointId sont des Arc<str> (moli-core/src/id.rs:11-20), Value::Text porte un Arc<str>, les appareils et les lignes de journal sont des Arc. Diffuser un événement à N abonnés coûte N incréments de compteur, pas N copies.
  • Verrous tolérants à l'empoisonnement (unwrap_or_else(PoisonError::into_inner), hub.rs:2794-2800) : une panique sous verrou ne condamne pas le hub.
  • Aucun verrou std n'est tenu à travers un .await : pour un futur Send (tous ceux des pilotes et de tokio::spawn), le compilateur le refuse. Cette garantie vient du système de types, pas d'une relecture.
  • L'ordre de prise des verrous est documenté (computed/mod.rs:1-2, mise en garde de coeur.md). Une recherche automatique sur les 39 méthodes qui prennent le verrou du modèle n'a trouvé aucune reprise de ce verrou déjà tenu.

2.4 Entrées et sorties

  • SQLite toujours hors des workers (spawn_blocking, moli-history/src/lib.rs:258-264, moli-energy/src/lib.rs:447-453). Trois connexions séparées pour l'historique : écrivain, lecteur, agents (store.rs:190-192). WAL et synchronous = NORMAL (store.rs:278-279), écritures par lots de 2 s ou 1 000 lignes (lib.rs:39-41), compactage borné quand l'écrivain sature (lib.rs:389-414). Le SQL des agents est en lecture seule, limité en taille et coupé à 2 s par un progress_handler (store.rs:294-306, 915-920). La purge tourne hors des workers, par lots de 5 000 lignes avec une pause de 2 ms (retention.rs:36-38).
  • Journal d'audit écrit par un thread dédié (journal_log.rs:55-59) : enregistrer une ligne ne touche jamais au disque depuis un worker.
  • États métier écrits par tokio::fs, avec fsync du fichier, renommage et fsync du dossier (state_file.rs).
  • Réseau commun (moli-net) : délai de 4 s par étape (lib.rs:45), corps bornés à 4 Mio et 16 Mio (lib.rs:53-56, 76-86), keepalive TCP 60 s puis 15 s contre les appareils débranchés sans bruit (lib.rs:400-404), TLS épinglé, connexion réutilisée pour les images de caméra, AbortOnDrop sur la tâche de connexion des requêtes uniques (once.rs:111-117).

2.5 Surfaces

  • Corps limités à 256 Kio par défaut, 4 Mio pour la voix et les imports (moli-api/src/lib.rs:62-64, 383). Quotas d'écriture par appelant et par classe (limit.rs). Flux SSE comptés : 8 par appelant, 64 au total (sse.rs:30-32).
  • Une panique dans un handler HTTP ne coûte que la connexion concernée (tâche hyper).
  • Les appels au LLM sont bornés (45 s pour une conversation, 10 à 30 s pour le reste : moli-assistant/src/llm.rs:12-19) et ne sont jamais sur le chemin d'un ordre.

2.6 Sûreté et sobriété

  • unsafe_code = "forbid" hérité par les 57 crates (Cargo.toml:109) : un pilote ne peut pas corrompre la mémoire d'un autre (les dépendances mises à part).
  • Briques dormantes tant qu'elles ne sont pas configurées (D1), pilotes à l'écoute plutôt qu'en sondage quand l'appareil le permet, release opt-level = "s", lto = "fat", codegen-units = 1, binaire musl statique sur scratch.
  • Le service d'archive (D13) tourne déjà dans un processus séparé : un précédent utile.

3. Les façons dont un module atteint encore la maison

3.1 Gel par appel bloquant ou calcul long Élevé

Le runtime n'a que deux workers par défaut (moli-os/src/config.rs:179-181, moli.example.toml:8). Tokio ne préempte pas : une tâche qui ne rend pas la main garde son worker. Un catch_unwind n'y peut rien, il n'y a pas de panique ; un timeout non plus, il ne s'applique qu'aux points d'attente.

Mesure E2 (machine de test, 2 workers, un pilote sain recevant un ordre toutes les 20 ms) :

Situation Ordres servis en 2 s Médiane Pire Retard max d'une minuterie de 10 ms
Référence 89 à 91 0,05 ms 0,1 à 6 ms 4 à 8 ms
1 pilote bloquant (200 ms sans rendre la main) 90 à 91 0,04 ms 0,1 à 4 ms 4 à 8 ms
2 pilotes bloquants 10 27 à 46 ms 34 à 58 ms 200 à 374 ms

Un appel bloquant est absorbé par le vol de tâches de Tokio ; deux suffisent à geler toute la maison : API, SSE, moteur d'automatismes, horloges et tous les autres pilotes partagent ces deux workers.

Le cœur est presque propre : SQLite, journal et états métier sont hors des workers ; seule exception, le coffre relit son petit fichier en std::fs avant d'écrire (moli-runtime/src/secrets.rs:163). Les sources trouvées sont dans les pilotes et quelques calculs faits sur place :

Source Où Coût
Décodage XML au coût quadratique en nombre d'attributs (roxmltree 0.21.1 cherche les doublons par balayage), fait en ligne dans l'async, plafonné à 1 Mio mais pas en attributs moli-netgear/src/xml.rs:16-34, moli-huawei-lte/src/xml.rs:14-26 mesuré (E8) : 0,16 s pour 64 Kio, 2,75 s pour 256 Kio, 96,6 s pour 1 Mio, à chaque cycle de 60 s si la réponse hostile revient ; le délai de 30 s du cycle ne peut pas l'interrompre
Rééchantillonnage FIR (63 coefficients) d'une phrase entière avant de la dire par la sonnette moli-reolink/src/talk.rs:37-40, moli-audio/src/pcm.rs:35-48 estimé 30 à 100 ms pour 10 s de voix sur la machine de test, davantage sur le Pi
Encodage FLAC d'une réponse vocale entière moli-assistant/src/satellite.rs:283-292 quelques ms à dizaines de ms selon la durée
Lectures /proc et /sys en std::fs dans la boucle moli-host/src/lib.rs:179-213, 638-704 microsecondes en général, dizaines de ms pour certains capteurs (drivetemp, nvme ; estimé)
std::fs::write sous Mutex std depuis des handlers async moli-phones/src/lib.rs:195-199 sensible sur carte SD
Gros JSON (2 à 4 Mio) parsés en ligne Z2M lib.rs:148, Overkiz /setup/devices, carte météo 10 à 40 ms, rarement
Agrégation d'un rapport d'énergie sur toute la plage moli-energy/src/lib.rs:323-339, report.rs:119-161 proportionnel à la plage demandée

Options étudiées :

Option Effet Coût
A. Lint clippy::disallowed_methods (std::fs::*, std::thread::sleep, std::net::*) dans les crates async, exceptions annotées Empêche à la compilation Faible
B. Détecteur de gel : une tâche mesure le retard d'une minuterie de 100 ms, journalise au-delà de 50 ms et publie le pire retard dans /api/health Détecte en production, y compris un interblocage Faible
C. Décodages et calculs lourds en spawn_blocking, avec un pré-contrôle bon marché (nombre d'attributs, taille) Supprime les sources connues Faible
D. Passer à 3 ou 4 workers sur un Pi Zero 2 W (4 cœurs) Plus de marge ; un worker inactif est parqué et ne coûte rien au repos Faible, à mesurer (RSS)
E. tokio-metrics par tâche supervisée (D8, décidée mais absente de Cargo.lock) Attribue le temps de worker à chaque pilote Moyen

Choix : A, B et C tout de suite (C en premier pour le XML), D après mesure sur le matériel cible, E avec la page Système.

3.2 Pilote figé, ou qui se dit prêt trop tôt Élevé

Le superviseur ne réagit qu'au retour ou à la panique de run (supervisor.rs:36-44). Un pilote qui attend indéfiniment reste running : chaque ordre échoue au bout de 5 s, la file finit pleine (Busy), et rien ne le relance (E3 : ordre en Timeout après 5,0 s, statut toujours running 10 s plus tard). Aucun indicateur de dernière activité n'est exposé.

La grille a trouvé des variantes de ce silence :

  • Prêt avant d'être connecté : ESPHome (moli-esphome/src/lib.rs:227) et Frigate (moli-frigate/src/lib.rs:365) appellent ctx.ready() avant toute connexion et gèrent leurs reconnexions en interne ; la panne du broker de Frigate n'est journalisée qu'en debug (lib.rs:438). Le superviseur ne voit jamais l'échec.
  • Parqué pour de bon : une seule réponse Invalid (une page HTML servie pendant un redémarrage du modem, par exemple) met ASUSWRT et Huawei LTE en attente d'un humain jusqu'au prochain redémarrage (moli-asuswrt/src/runtime.rs:166-173, moli-huawei-lte/src/runtime.rs:176-192) ; Netgear, lui, repart avec attente croissante.
  • Connexion à moitié ouverte : le keepalive TCP n'est posé que par PinnedHttps::connect (moli-net/src/lib.rs:400), pas par PinnedTls::connect (l. 286-303) ni WebSocket::open (ws.rs:67-83). Le WebSocket cloud de Tuya envoie un ping mais n'attend pas le pong (moli-tuya/src/cloud.rs:423-426) : une connexion morte n'est vue qu'à la fin des retransmissions TCP (de l'ordre du quart d'heure), et les capteurs endormis (fuite, porte) restent muets jusqu'à la resynchronisation de 30 min.
  • Adresse figée : Roborock résout l'hôte une seule fois et ne retourne jamais (moli-roborock/src/lib.rs:103) ; une adresse DHCP qui change le laisse injoignable sans relance.

Options étudiées :

Option Effet Coût
A. Vivacité gérée par le superviseur : DriverCtx note la dernière progression (événement publié, ordre pris, ready) dans un AtomicU64 ; chaque pilote déclare un silence maximal ; le select! du superviseur gagne une branche qui abandonne run et relance Attrape aussi les cas inconnus Moyen
B. Règles de revue : ready() seulement après la première réponse ; toute attente réseau sous délai ou keepalive (keepalive ajouté à PinnedTls et WebSocket) ; ping/pong vérifié Prévient Faible
C. N ordres consécutifs en Timeout déclenchent une relance Signal gratuit, déjà disponible Faible

Choix : A (générique) et C (immédiat), B comme règles de revue et petites corrections. Abandonner le futur de run ne marche qu'aux points d'attente : un pilote bloquant (3.1) reste hors d'atteinte.

3.3 Briques hors superviseur Élevé

Le dépôt contient un seul catch_unwind : celui des pilotes (supervisor.rs:38). Les briques sont lancées par un simple tokio::spawn et leur handle n'est attendu qu'à l'arrêt (moli-os/src/main.rs:490-500) :

Brique Lancement Si elle panique
Moteur d'automatismes moli-automation/src/lib.rs:315 plus aucun automatisme ne se déclenche
Historique (enregistreur, écrivain, purge) moli-history/src/lib.rs:146-172 l'historique s'arrête
Énergie (enregistreur) moli-energy/src/lib.rs:166 kWh et € ne sont plus comptés
Ordonnanceur des minuteurs main.rs:1542 les minuteurs n'expirent plus
Entretien (expiration des demandes, cache d'état) main.rs:925 les demandes n'expirent plus, state.json n'est plus écrit
Horloges des calculs et des dépendances computed_clock.rs:16, dependency_hub.rs:444 valeurs calculées figées ; l'indicateur « démarrée » reste vrai, rien ne les relance

E4 le montre : une brique abonnée au bus meurt au troisième événement, la maison continue, personne n'est prévenu. Les causes possibles existent : invariants en expect ou unwrap (dependencies/store.rs, douze unwrap après chargement ; computed/engine.rs:187 ; scene_hub.rs:316). Aucun n'est un bogue aujourd'hui, chacun est un arrêt silencieux potentiel demain. Les sous-tâches lâchées par les pilotes ont le même défaut à plus petite échelle (section 5.4).

Options étudiées :

Option Effet Coût
A. supervise(nom, fabrique) générique, même boucle que spawn_driver (capture, attente croissante, statut publié dans l'instantané et /api/health) Auto-guérison Moyen : chaque brique doit pouvoir repartir (réabonnement, instantané ; l'historique et le moteur savent déjà le faire après un Lagged)
B. Sentinelle : un JoinSet des briques ; à toute sortie, journal, notice et santé « dégradée » Plus de panne silencieuse Faible
C. Arrêt volontaire du processus si une brique meurt (Docker relance) État propre garanti Faible, mais toute la maison redémarre

Choix : B d'abord, puis A pour le moteur, l'historique, l'énergie et les minuteurs. C reste une solution honnête pour une brique qui ne sait pas repartir.

3.4 Fautes de processus Moyen

Tout tourne dans un seul processus. Un débordement de pile, un échec d'allocation, un dépassement du plafond mémoire du conteneur (mem_limit: 128m, compose.yaml:18), une double panique ou un abort arrêtent toute la maison : E7 provoque un débordement de pile dans un pilote, le processus sort en code 134 (SIGABRT), le superviseur n'a rien vu. Docker relance (restart: unless-stopped, compose.yaml:11) : la maison est indisponible le temps du démarrage (budget 2 s) et des reconnexions ; les dernières valeurs reprises datent d'au plus une minute (main.rs:705-707). Si la faute vient d'une entrée qui revient à chaque connexion, la relance tourne en boucle.

Exposition constatée : faible. Aucune récursion non bornée sur des données réseau (serde_json s'arrête à 128 niveaux, roxmltree est itératif et limite les entités à 10 niveaux, les parcours internes sont bornés, par exemple moli-automation/src/check.rs:980 ou moli-asuswrt/src/json.rs:7-26), corps de réponse bornés, unsafe interdit. Un seul point d'allocation non plafonné a été relevé : moli-audio::pcm::resample ne borne pas la taille de sortie (pcm.rs:52-63) ; les appelants actuels passent des fréquences sûres.

Options étudiées :

Option Effet Coût
A. Garder un seul processus, maintenir les règles (pas de récursion sur une entrée réseau, tailles bornées) et fuzzer les décodeurs exposés (trames ESPHome, Tuya, SOAP, XML) Prévient Faible à moyen
B. Disjoncteur de redémarrage : après 3 démarrages anormaux en 10 min, démarrer sans les pilotes qui démarraient au moment des pannes, et le dire Évite la boucle Moyen
C. Processus séparés pour les pilotes à risque, reliés au hub par une socket locale, comme l'archive Vrai confinement mémoire et pile Élevé (IPC, empaquetage, mémoire)

Choix : A. C ne se justifie que si un pilote non relu doit tourner, ou si un décodeur ne peut pas être durci ; B seulement si une boucle est observée.

3.5 Démarrage couplé Moyen

spawn_drivers propage toute erreur de construction (main.rs:1111-1162, ? aux lignes 1123 à 1153), et serve s'arrête (main.rs:436). Or certaines constructions lisent des données d'exécution, pas seulement la configuration :

  • moli_phones::open lit phones.json ; illisible, c'est une erreur (moli-phones/src/lib.rs:179-185). Ce fichier est écrit sans fsync (lib.rs:195-199) : une coupure de courant au mauvais moment peut le laisser vide.
  • ProfileDriver::new lit le fichier de profil (moli-profile/src/lib.rs:314-315).
  • L'ouverture de l'historique, de l'énergie et des automatismes est aussi fatale (main.rs:420-434, 462).

Scénario : une coupure pendant l'écriture de phones.json, et la maison entière refuse de démarrer ; le tableau de bord, éteint, ne peut même pas le dire.

Refuser une configuration invalide au démarrage reste juste (check-config fait la même chose). Le problème, ce sont les données. Recommandation : à serve, un pilote dont la construction échoue est inscrit avec un statut d'attente qui dit pourquoi, les autres démarrent ; phones.json passe par l'écriture atomique synchronisée déjà utilisée ailleurs. Le cas des bases (historique, énergie) mérite une décision : démarrer sans elles en le signalant, ou attendre un humain.

4.3 Le moteur d'automatismes : une seule file Moyen

  • Une seule boucle traite tous les événements de la maison (engine.rs:72-98). Pour un appui (occurrence), elle attend l'admission durable, avec fsync (occurrences.rs:164), et les verrous des minuteurs ; pendant ce temps, aucun autre déclencheur n'est examiné.
  • Sur Lagged, les valeurs sont relues mais les transitions manquées sont perdues (engine.rs:77-85) : un « quand la porte s'ouvre » survenu pendant le retard ne partira jamais. Le journal le signale, c'est honnête, mais c'est une perte.
  • Chaque changement d'état parcourt tous les automatismes actifs et tous leurs déclencheurs, et alloue une String (engine.rs:351-357) ; la carte last (HashMap<String, Value>) recopie l'état que le hub connaît déjà.
  • L'horloge bat à 1 Hz, reparcourt tout, formate une date à chaque seconde et recalcule le soleil pour chaque déclencheur solaire (engine.rs:499-536), alors que tous les déclencheurs horaires sont à la minute.
  • Chaque exécution en attente (WaitFor) réévalue sa règle à chaque événement de la maison (run.rs:427-445).

Recommandations : indexer les déclencheurs d'état par point, comme occurrence_index le fait déjà pour les appuis ; garder last sous clé PointId ou, mieux, porter la valeur précédente dans Event::State (le hub la connaît sous son verrou d'écriture) ; une horloge qui dort jusqu'à la prochaine minute due ; sortir l'admission durable de la boucle de distribution ; sur Lagged, comparer l'instantané relu aux valeurs connues pour rejouer les transitions franches.

5. Pilotes et services tiers

Lecture des 45 crates de pilotes et de briques selon la même grille : structure de la boucle, durée de vie des sous-tâches, attentes sans délai, appels bloquants, croissance non bornée, surface de panique, coût au repos, verrous. Tableau complet par crate en annexe B.

5.1 Ce que la grille ne trouve pas

  • Aucun std::thread::sleep, aucun std::net synchrone, aucun block_on dans le code de production des pilotes.
  • Aucun canal non borné ; tous les tampons réseau sont plafonnés (MQTT 4 Mio, SSE et WebSocket 1 Mio, Cast 256 Kio, ESPHome 32 Kio, Tuya 4 Kio…).
  • Des décodeurs qui vérifient longueur, somme de contrôle ou signature avant d'indexer (Tuya, miIO de Roborock, protobuf d'Android TV, DNS de Cast, RTSP de Reolink).
  • Des unwrap et expect de production limités à des invariants (clé ring, aléa système).

8. Limites de cette analyse

  • Lecture du code et expériences synthétiques : aucun test de charge sur de vrais appareils, aucune mesure sur le Pi Zero 2 W. Les durées marquées « estimé » ne sont pas mesurées.
  • La bascule vers Turso (D13, ticket C1) n'est pas encore dans main : la partie stockage porte sur rusqlite.
  • La grille des pilotes est une lecture statique ; les constats élevés ont été revérifiés dans le code, les autres sont rapportés tels que la grille les a relevés.
  • Hors champ : interface web, application mobile, internes du service d'archive (processus séparé, hors du domaine de panne du cœur), décodeurs tiers (symphonia).

fn status(hub: &Hub, instance: &str) -> String {
    hub.snapshot()
        .drivers
        .iter()
        .find(|d| d.instance.as_str() == instance)

/// Latences d'ordres successifs vers le pilote sain pendant `pendant`.
async fn ordres(hub: &Hub, pendant: Duration) -> (usize, usize, Duration, Duration) {
    let p = point("sain");
    let fin = Instant::now() + pendant;
    let (mut ok, mut ko, mut toutes) = (0, 0, Vec::new());
    let mut v = false;
    while Instant::now() < fin {
        v = !v;
        let t = Instant::now();
        match hub.command(&p, Value::Bool(v), Origin::Ui, None).await {
            Ok(()) => ok += 1,
            Err(_) => ko += 1,
        }
        toutes.push(t.elapsed());
        tokio::time::sleep(Duration::from_millis(20)).await;
    }
    toutes.sort();
    let med = toutes.get(toutes.len() / 2).copied().unwrap_or_default();
    let max = toutes.last().copied().unwrap_or_default();
    (ok, ko, med, max)
}

/// Retard maximal d'une minuterie de 10 ms (latence d'ordonnancement).
fn sonde(stop: CancellationToken) -> (Arc<AtomicU64>, tokio::task::JoinHandle<()>) {
    let pire = Arc::new(AtomicU64::new(0));
    let p = pire.clone();
    let h = tokio::spawn(async move {
        while !stop.is_cancelled() {
            let t = Instant::now();
            tokio::time::sleep(Duration::from_millis(10)).await;
            let retard = t.elapsed().saturating_sub(Duration::from_millis(10));
            p.fetch_max(u64::try_from(retard.as_micros()).unwrap(), Ordering::Relaxed);
        }
    });
    (pire, h)
}

/// Un parseur récursif naïf, comme on en écrit pour du XML ou du JSON maison :
/// il construit l'arbre des éléments imbriqués.
#[derive(Debug)]
enum Noeud {
    Liste(Vec<Noeud>),
}

#[inline(never)]
fn analyser(octets: &[u8], i: &mut usize) -> Noeud {
    let mut enfants = Vec::new();
    while *i < octets.len() && octets[*i] == b'[' {
        *i += 1;
        enfants.push(analyser(std::hint::black_box(octets), i));
    }
    Noeud::Liste(enfants)
}

fn profondeur(octets: &[u8]) -> usize {
    let mut i = 0;
    let arbre = analyser(octets, &mut i);
    let Noeud::Liste(enfants) = std::hint::black_box(&arbre);
    let n = enfants.len() + i;
    std::mem::forget(arbre);
    n
}
